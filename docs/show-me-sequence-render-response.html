assistant.py → render_response(pending.request, content="", ...)
  • request is the text passed to the agent. Regeneration resolves the original generation request from its parent snapshot.
  • content is a prefix displayed immediately and prepended to all final public text.
  • key namespaces the catalog and sequence widget containers.
  • pending carries the request UUID, acceptance time, generation flag and regeneration source. If supplied, its flag overrides the method’s require_generation argument.

Without pending, the method creates a fresh PendingResponse. message_index is used by the caller when saving the result.

ResponseProgressRenderer.accept() first checks the request UUID and shifts producer timestamps to include the time since the UI accepted the request. It delegates state reduction to ResponseExecution.accept().

  • Reject a foreign request UUID.
  • Reject an event index ≤ the last accepted index, or any event after the terminal result.
  • Suppress duplicate public messages with the same (purpose, message_id).
  • Store execution state, update step rows and refresh the status label before the outer method draws content.

Step references are expected to be valid and ordered by the producer; the reducer does not validate every step reference itself.

The producer normally emits its terminal error before raising. fail() is idempotent when a terminal event already exists. It also covers factory failures where no event stream was created.

  • finish() synthesizes an error if the stream ended without a terminal event, redraws all step rows, sets the final status and displays any public error.
  • No committed sequence → clear the temporary sequence gallery.
  • A committed sequence survives a later model failure. Catalog output is also retained if it was already displayed.

The try/except covers factory initialization and event consumption. Final snapshot creation and variant lookup occur after that catch block.

Regenerate updates the existing card and archives its previous execution. If regeneration fails before commit, the old sequence remains on that card. A new sequence can clear an old reply even when its new reply is empty.

History replay renders saved execution snapshots, catalog items, sequence controls and final text. Variant UUIDs allow views to be rebuilt from agent state. Browsing variants updates the selected sequence without another model call.

“Saved” here means this session: chat lives in st.session_state, and the agent uses InMemorySaver. Catalog import is a separate history-card action.

Commit · preview → saved variant

The confirmation handshake

Tool builds a complete variant

commit_sequence() returns a Command containing the full snapshot, active_sequence_uuid, turn_operation_committed=True and a compact ToolMessage.

Middleware announces a pending commit

For a successful state-changing Command, it emits PendingSequenceCommit and defers the tool’s StepFinishedEvent.

The graph applies and checkpoints state

The stream uses sync durability so get_state() can read the variant before the UI is told it exists.

ResponseProgress checks merged values

The UUID must exist in sequences, equal active_sequence_uuid, and have turn_operation_committed=True. Each UUID is confirmed once.

Commit, then finish the tool step

Emit SequenceCommittedEvent, then StepFinishedEvent. The UI fetches the saved snapshot and replaces the preview.

ChatMessage
├─ content                    final public text
├─ execution                  public attempt history
│  ├─ outcome, duration, error
│  ├─ source_sequence_uuid / sequence_uuid
│  ├─ steps + progress
│  └─ intermediate_messages
├─ sequence                   selected display projection
├─ sequence_variants          family display projections
├─ sequence_variant_uuids     links to full stored variants
├─ sequence_request           original generation request
├─ selected_sequence_index

ExecutionSnapshot excludes final text and gallery payloads. Those belong to the other ChatMessage fields and agent state.
