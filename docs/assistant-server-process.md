# Как работает сервер ассистента: от `assistant.py` до каталога и обратно

Документ описывает фактический код проекта на 12 октября 2026 года, включая текущие изменения рабочей копии. Читаем приложение в порядке выполнения: начинаем с `assistant.py`, при вызове переходим внутрь функции или метода, затем возвращаемся к вызывающему коду. Условные ветки, например Regenerate и Save, разбираются после основного пути запроса.

Это описание реализации. Планы и приёмка находятся в спецификациях [ассистента (001)](specs/001-create-assistant-agent/README.md), [прогресса ответа (002)](specs/002-assistant-response-progress/README.md), [показа каталога (003)](specs/003-catalog-items-display/README.md), [обмена элементов (006)](specs/006-swap-sequence-elements/README.md) и [добавления элементов (007)](specs/007-add-sequence-elements/README.md).

## 1. Что запускается и где проходит граница сервера

Точка входа — [src/langchain_app/assistant.py](../src/langchain_app/assistant.py). Запуск из корня проекта:

```bash
uv run --env-file .env streamlit run src/langchain_app/assistant.py
```

HTTP-сервер и связь с браузером предоставляет Streamlit. В `assistant.py` нет собственных обработчиков HTTP-маршрутов: файл строит интерфейс и запускает Python-логику в ответ на взаимодействия пользователя.

В обработке участвуют четыре стороны:

| Сторона | Что выполняет |
| --- | --- |
| Браузер пользователя | Показывает Streamlit-интерфейс, отправляет ввод, загружает изображения по URL, выполняет JavaScript кнопки Save |
| Python-процесс Streamlit | Выполняет `assistant.py`, хранит состояние сессии, запускает агента, обращается к каталогу и TypeSafe |
| Языковая модель ассистента | Интерпретирует запрос, выбирает инструменты и их аргументы, пишет ответ пользователю |
| Внешние сервисы | Asana Catalog возвращает реальные асаны и теги; TypeSafe/Jev выбирает следующую позу из предложенных кандидатов |

Основной путь запроса выглядит так:

```text
assistant.py → callback → PendingResponse → отключение контролов
  → SequenceRenderer.render_response()
    → ResponseProgressRenderer: Thinking... до создания зависимостей
    → резервирование отдельных областей текста, каталога и секвенции
    → session_assistant() → get_assistant_agent()
    → AssistantAgent.stream_response_events(request_id=...)
      → request_started → create_agent(...)
      → stream_events(version="v3", transformers=[CustomTransformer], durability="sync")
      → interleave("custom", "values") → ResponseProgress
      → модель → инструмент → модель
        generate_sequence → SequenceGenerator → каталог / Jev
          → sequence_element → подтверждение состояния → sequence_committed
        search_catalog_items → проверенные кандидаты в latest_catalog_items
        show_catalog_items → проверка ID → catalog_items_displayed
        replace_sequence_element → новый вариант → sequence_committed
        swap_sequence_elements → обмен вхождений → новый вариант → sequence_committed
        add_sequence_elements → SequenceGenerator.add_elements → каталог / Jev
          → прогресс блока → insert_elements → новый вариант → sequence_committed
      → assistant_message(final) → request_finished
    → фильтрация request_id / event_index → живые области UI
    → ChatMessage(content, execution, catalog_items?, sequence, ...)
  → сохранение сообщения → очистка pending_response → st.rerun()
```

Поиск сам по себе не показывает каталог. Событие `catalog_items_displayed`
появляется только из успешного `show_catalog_items`. Потоковые позы генерации
относятся к секвенции и поступают отдельными `sequence_element`.

`create_agent()` строит агентный граф LangChain на runtime LangGraph. Граф выполняет цикл «модель → инструмент → модель», а сервис `SequenceGenerator` реализует алгоритм подбора поз. Это два разных уровня принятия решений: модель выбирает действие, Jev выбирает конкретную следующую позу.

## 2. Начало `assistant.py`: импорты, настройки, состояние

### 2.1. Импорты

Сначала Python импортирует `os`, `cast`, Streamlit, `load_dotenv`, фабрику `get_assistant_agent`, схемы и `SequenceRenderer`.

`langchain_app.schemas`, `langchain_app.services` и `langchain_app.ui` через свои `__init__.py` экспортируют классы из отдельных модулей. Импорт делает определения доступными, но сам по себе не создаёт экземпляр ассистента и не запускает генерацию.

`cast(list[ChatMessage], ...)` далее нужен для статической типизации. Он не преобразует данные и не проверяет их содержимое во время выполнения.

### 2.2. `load_dotenv()` и переменные окружения

`load_dotenv()` загружает переменные из `.env`. При обычном использовании уже заданные переменные окружения сохраняют приоритет. Флаг `uv run --env-file .env` также передаёт окружение запускаемому процессу.

Следом файл задаёт:

```python
SEQUENCE_LANGUAGE = "en"
ASANA_SERVICE_BASE_URL = os.getenv("ASANA_SERVICE_BASE_URL", "http://0.0.0.0:4999")
ASANA_CATALOG_FOLDER_UUID = os.getenv("ASANA_CATALOG_FOLDER_UUID", "yoga-public-v1")
```

`SEQUENCE_LANGUAGE` определяет язык данных создаваемых карточек. Клиенты каталога дополнительно закрепляют английский язык непосредственно в HTTP-запросе. Русскоязычный запрос пользователя не переключает каталог на русский: ответ ассистента должен быть по-русски, а имена асан и тегов остаются такими, какими пришли из английского API.

`ASANA_SERVICE_BASE_URL` используется и Python-клиентами, и кнопкой Save. Для Save браузер должен открывать тот адрес каталога, на котором пользователь авторизуется.

`ASANA_CATALOG_FOLDER_UUID` выбирает публичную папку, внутри которой сервер ищет позы и теги.

Остальные настройки читаются позже, при создании зависимостей или внутри библиотек:

| Переменная | Назначение |
| --- | --- |
| `ASSISTANT_AGENT_MODEL` | Основное имя модели ассистента |
| `SEQUENCE_AGENT_MODEL` | Запасное старое имя настройки, если основное пусто |
| `OPENAI_API_KEY` | Доступ к OpenAI при стандартной конфигурации модели |
| `TYPESAFE_API_KEY` | Доступ к TypeSafe/Jev |
| `LANGSMITH_TRACING`, `LANGSMITH_API_KEY`, `LANGSMITH_PROJECT`, `LANGSMITH_ENDPOINT` | Настройки трассировки библиотечных вызовов |

Пример имён и значений находится в [.env.example](../.env.example). Сам код не загружает ключи из сообщения пользователя.

### 2.3. Заголовок и история интерфейса

`st.title("Sequence Generator")` выводит заголовок.

Затем:

```python
st.session_state.setdefault("messages", [])
messages = cast(list[ChatMessage], st.session_state.messages)
```

При первом выполнении создаётся пустой список сообщений. При следующих выполнениях используется тот же список текущей сессии. Переменная `messages` ссылается на него: `messages.append(...)` сразу меняет `st.session_state.messages`.

Streamlit повторно выполняет файл сверху вниз при соответствующих действиях пользователя. Поэтому обычные локальные переменные пересоздаются, а значения в `st.session_state` позволяют сохранить историю между проходами.

Эта история содержит видимые пользователю сообщения и сведения о карточках. История для модели хранится отдельно в состоянии агентного графа; её разберём при создании `AssistantAgent`.

### 2.4. Определение `session_assistant()`

Функция объявляется здесь, но при объявлении не выполняется:

```python
def session_assistant() -> AssistantAgent:
    if "assistant_agent" not in st.session_state:
        st.session_state["assistant_agent"] = get_assistant_agent(
            ASANA_SERVICE_BASE_URL, ASANA_CATALOG_FOLDER_UUID,
        )
    return st.session_state["assistant_agent"]
```

При первом вызове она создаст ассистента и сохранит его в состоянии текущей сессии. Следующие вызовы вернут тот же объект. Это сохраняет диалог, варианты последовательностей и выбор активного варианта при перерисовках страницы.

Переход внутрь `get_assistant_agent()` отложен до раздела 6: при первом открытии страницы без сообщений и запроса эта функция ещё не вызывается.

## 3. Форма Generate и создание рендерера

### 3.1. Форма `sequence-generation-form`

`with st.form(..., border=False)` объединяет выбор количества и кнопку отправки. Внутренний горизонтальный контейнер располагает их рядом.

`st.selectbox()` предлагает числа из `range(9, 37)`, то есть от 9 до 36 включительно. `index=0` выбирает 9 по умолчанию. Ключ `sequence-elements-count` связывает значение со Streamlit-состоянием виджета.

`st.form_submit_button("Generate", ...)` возвращает признак отправки формы в этом проходе. Изменения внутри формы передаются приложению вместе при её отправке.

Диапазон 9–36 относится к этой форме. Текстовый запрос проходит через отдельное определение `count` моделью; обязательный верхний предел для любой генерации — 45 элементов. Он закреплён в промпте, схеме инструмента и генераторе.

### 3.2. `SequenceRenderer.__init__()`

Далее `assistant.py` создаёт [SequenceRenderer](../src/langchain_app/ui/sequence.py):

```python
SequenceRenderer(
    generator_factory=session_assistant,
    language=SEQUENCE_LANGUAGE,
    catalog_url=ASANA_SERVICE_BASE_URL,
)
```

Несмотря на историческое имя `generator_factory`, сюда передаётся функция, возвращающая `AssistantAgent`.

Конструктор сохраняет четыре значения: размер миниатюр, по умолчанию 64 пикселя, фабрику ассистента, язык и адрес каталога. Он не вызывает фабрику и не запускает внешние запросы.

### 3.3. `SequenceRenderer.render_styles()`

Следующая строка вызывает `render_styles()`. Метод через `st.html()` добавляет CSS:

- размер и форму миниатюр, `object-fit: cover` и скругление углов;
- зелёные скобки по сторонам изображения для `start_mirror` и `end_mirror`;
- скрытие панели инструментов элементов через CSS-селектор.

Этот метод отвечает за отображение. Он не меняет асаны, порядок или mirror-флаги.

После его завершения возвращаемся в `assistant.py` к `render_messages(messages)`.

## 4. Отрисовка истории до обработки нового запроса

### 4.1. `SequenceRenderer.render_messages()`

Метод перебирает сохранённые сообщения по порядку. Для каждого он:

1. Открывает `st.chat_message(message["role"])`.
2. Воспроизводит `execution_history` и `execution` через `render_execution()`.
3. Выводит непустой `message["content"]` как Markdown.
4. При непустом `catalog_items` вызывает `CatalogItemsRenderer.render()` с ключом `assistant-catalog-<индекс>`.
5. Вызывает `_render_message_sequence(messages, message_index)` для возможной карточки последовательности.

Каталожная подборка восстанавливается из отделённого списка `CatalogItemSchema` в самом сообщении. Этот путь не получает ассистента, не запускает модель или поиск и не добавляет UI-снимок в prompt. Старые сообщения без поля `catalog_items` остаются совместимыми. Каталог и секвенция занимают отдельные области после текста.

При первом открытии страницы список пуст, поэтому цикл ничего не делает. При последующих проходах он восстанавливает весь видимый диалог.

### 4.2. `_render_message_sequence()`: восстановление карточки

Сначала метод читает `sequence_variant_uuids`. Если UUID вариантов есть и фабрика доступна, вызывается `session_assistant()`.

Для каждого UUID выполняется `assistant.get_sequence(uuid)`. Внутри этого метода:

1. Свойство `state` читает `self._agent.get_state(self._config).values`; если граф ещё не создан, используется пустой словарь.
2. `deepcopy()` возвращает отделённую копию состояния. Изменение полученного словаря не меняет сохранённую историю.
3. По UUID выбирается snapshot из `sequences`.
4. `GeneratedSequence.from_snapshot()` восстанавливает Pydantic-модель из словаря.

`from_snapshot()` исключает сохранённое поле `elements_count` перед валидацией: количество вычисляется из `elements`, поэтому нельзя принять два противоречивых значения.

Если найдены все варианты, каждый преобразуется через `generated_sequence_view()` в данные для интерфейса, и выбранный вариант записывается в `message["sequence"]`. Сохранённые полные snapshots остаются источником данных; карточки можно построить заново.

Если хотя бы один snapshot отсутствует, локальная переменная `assistant` сбрасывается в `None`. Метод продолжает показывать сохранённую карточку, но не считает её полноценным контекстом для выбора и редактирования.

### 4.3. `generated_sequence_view()`

Эта функция выполняет проекцию полного варианта в `SequenceView`:

- `info` содержит `id=0`, UUID варианта, имя, описание, язык и вычисленное число элементов;
- `thumbnails` содержит для каждого элемента UUID асаны каталога, порядок, URL изображения, имя и два mirror-флага.

`id=0` означает локально созданную последовательность, у которой ещё нет числового ID сохранённой записи каталога.

Если изображения нет, функция оставляет элемент с пустой строкой `image_url`. Сохранённая структура последовательности от этого не сокращается; рендерер сможет показать имя вместо изображения.

### 4.4. Совместимость со старыми сообщениями

Если нет `message["sequence"]`, метод пробует старые поля `sequence_info` и `thumbnails`. Если последовательности нет ни в новом, ни в старом формате, метод возвращается: это обычное текстовое сообщение.

Для карточки через `setdefault()` инициализируются:

- `sequence_variants` — список отображаемых вариантов;
- `selected_sequence_index` — индекс выбранного варианта, по умолчанию 0.

Если отсутствует `sequence_request`, метод ищет ближайшее предшествующее сообщение с ролью `user` и сохраняет его текст. Это запасной путь для старой истории. У новых карточек исходный запрос берётся из полноценного snapshot.

### 4.5. Кнопки и вывод карточки

Метод создаёт уникальные ключи на основе индекса сообщения, например `assistant-sequence-3`.

Затем строятся Regenerate, отметка Active sequence или кнопка Use this sequence, а при нескольких вариантах — Previous Sequence и Next Sequence. Обработчики этих действий разобраны в разделе 16.

В обычном проходе без нажатия кнопок метод вызывает `self.render(variants[selected], key=key)`.

Внутри `render()`:

1. При `sequence is None` выполняется выход.
2. `_render_info()` выводит имя, необязательное описание и подпись с ID, числом поз и языком. Если число равно 0, число поз не выводится.
3. `_render_images()` перебирает миниатюры внутри горизонтального контейнера с переносом строк.

Для непустого `image_url` вызывается `_thumbnail_html()`. Он собирает `<img>` и нужные скобки. URL и alt-текст проходят через `html.escape(..., quote=True)` перед вставкой в HTML-атрибуты. Python передаёт браузеру URL; скачивание самой картинки для показа выполняет браузер.

Если URL пуст, `_render_images()` выводит название через `st.caption()`.

После карточки вызывается `render_sequence_import()`, если задан адрес каталога. Это создаёт кнопку Save, но не сохраняет последовательность автоматически. Для старой локальной карточки с `id=0` и без UUID перед этим назначается UUID.

После обработки всех сообщений `render_messages()` завершается. Возвращаемся к следующим строкам `assistant.py`: формированию нового запроса.

## 5. Получение нового запроса в `assistant.py`

Generate вызывает callback `generate_sequence()`, который формирует текст
`Generate a yoga sequence with <число> poses.`, заполняет поле ввода и ставит
`PendingResponse(request, require_generation=True)` через `enqueue_response()`.
Чат вызывает `submit_chat()` и ставит обычный `PendingResponse(request)`.
Regenerate передаёт также UUID источника и индекс существующего сообщения.

`enqueue_response()` не принимает второй запрос, пока первый выполняется.
Для нового сообщения callback сразу добавляет пользователя в историю.
Следующий проход показывает историю и отключённые Generate, поле ввода,
Regenerate и навигацию вариантов до начала работы модели.

При наличии `pending_response` точка входа вызывает:

```python
response = sequence_renderer.render_response(
    pending.request, content="", key="assistant-sequence-live", pending=pending,
)
```

Для нового запроса сохраняется любой ответ, включая ошибку и отсутствие текста.
Для Regenerate обновляется существующая карточка; предыдущее выполнение
сохраняется через `retain_execution()`. В `finally` очищается `pending_response`,
после чего выполняется `st.rerun()`. Существующее поле `catalog_items` сообщения
не изменяется Regenerate: обязательная генерация не допускает показ каталога.

## 6. `render_response()` и создание зависимостей

Исходники: [ui/sequence.py](../src/langchain_app/ui/sequence.py), [dependencies.py](../src/langchain_app/dependencies.py), [services/assistant_agent.py](../src/langchain_app/services/assistant_agent.py).

### 6.1. Получение ассистента

Сначала создаётся `ResponseProgressRenderer` со статусом Thinking... и резервируются три `st.empty()` для текста, каталога и секвенции. Только после этого вызывается фабрика зависимостей. Поэтому начальная обратная связь видна и при медленной инициализации или её ошибке.

`render_response()` проверяет наличие фабрики; иначе выбрасывает `ValueError`.

Следом выполняется `assistant = self._generator_factory()`, то есть `session_assistant()`. Если ассистент уже есть в сессии, он просто возвращается. Для первого запроса переходим в `get_assistant_agent(base_url, catalog_folder_uuid)`.

### 6.2. `get_assistant_agent()` → `get_sequence_generator()`

Сначала фабрика получает `generator = get_sequence_generator(...)`.

`get_sequence_generator()` помечена `@st.cache_resource`. При первом вызове для этих аргументов она создаёт `SequenceGenerator`, передавая ему:

- `get_catalog_item_service(base_url, catalog_folder_uuid)`;
- `get_type_safe_service()`.

Обе функции тоже используют `st.cache_resource`.

`get_catalog_item_service()` создаёт `CatalogItemService`. Его конструктор наследуется от `CatalogClient`: он проверяет непустые адрес и UUID папки, формирует URL папки и создаёт HTTP-клиент. Детали транспорта разобраны в разделе 11.

`get_type_safe_service()` создаёт `TypeSafeService`. Внутри `TypeSafeService.__init__()` сохраняется переданный классификатор либо создаётся `TypeSafeClassifier()`.

`SequenceGenerator.__init__()` только сохраняет оба сервиса в полях экземпляра. Подбор поз пока не выполняется.

Зависимости инициализируются на потоке выполнения Streamlit-скрипта, до входа в инструменты агента. Поэтому инструменту не нужно обращаться к Streamlit-кэшу во время своего исполнения: его `generator_factory` вернёт уже подготовленный генератор.

### 6.3. Создание `AssistantAgent`

Далее `get_assistant_agent()` создаёт `AssistantAgent`, передавая:

- `generator_factory=lambda: generator` — функцию для получения уже созданного генератора;
- тот же кэшируемый `CatalogItemService`;
- кэшируемый `CatalogTagService`, создаваемый `get_catalog_tag_service(...)`;
- выбранное имя модели.

Имя модели определяется последовательно:

1. Непустой `ASSISTANT_AGENT_MODEL` после `.strip()`.
2. Непустой `SEQUENCE_AGENT_MODEL` после `.strip()`.
3. Литерал `openai:gpt-5.5`, заданный в коде.

`get_assistant_agent()` не помечена кэшированием ресурсов. В отличие от клиентов и генератора, ассистент с историей создаётся для конкретной Streamlit-сессии и затем хранится в её `session_state`.

Кэш ресурсов по умолчанию может использоваться разными сессиями одного процесса для одинаковых аргументов. В этих сервисах не хранится история конкретного диалога: она находится внутри отдельного `AssistantAgent`.

### 6.4. `AssistantAgent.__init__()`

Конструктор сохраняет фабрику генератора, сервисы каталога и модель. Затем:

```python
self._agent = None
self._checkpointer = InMemorySaver()
self._config = {
    "configurable": {"thread_id": str(uuid4())},
    "recursion_limit": 20,
}
```

`_agent=None` откладывает создание графа до первого исполнения запроса.

`InMemorySaver` хранит checkpoints графа в памяти процесса. У каждого ассистента свой saver и свой UUID `thread_id`. Все запросы этого экземпляра используют тот же thread, поэтому граф продолжает предыдущую историю.

`recursion_limit=20` ограничивает число шагов выполнения графа. Это не лимит числа поз и не буквальное число вызовов инструментов: один проход может включать разные узлы и middleware.

Возвращаемся через `get_assistant_agent()` в `session_assistant()`: экземпляр сохраняется под ключом `assistant_agent`. Затем возвращаемся в `render_response()`.

### 6.5. Один поток событий и три области вывода

`render_response()` потребляет `assistant.stream_response_events()` с UUID из
`PendingResponse`. Сначала каждое событие проходит `progress.accept(event)`:
чужой `request_id`, повторный или меньший `event_index`, а также события после
`request_finished` отклоняются. UI обновляется только для принятого события.

Финальный текст собирается из `AssistantMessageEvent(purpose="final")` в
`progress.execution.final_texts`. `SequenceElementEvent` обновляет временную
секвенцию; `SequenceCommittedEvent` получает подтверждённый полный вариант из
ассистента. `CatalogItemsDisplayedEvent` копируется через `model_copy(deep=True)`
и немедленно передаётся `CatalogItemsRenderer` в зарезервированную область
после текста, вне статуса. Искусственной задержки нет. За ответ UI принимает
первую подтверждённую подборку; повторная не заменяет её.

### 6.6. Завершение ответа

`progress.finish()` создаёт `ExecutionSnapshot` и показывает публичную ошибку,
если она есть. Неподтверждённая секвенция очищается. Уже показанная каталожная
подборка остаётся даже при ошибке следующего model call и при пустом тексте.
Она возвращается в необязательном `ChatMessage.catalog_items`; без события
показа поле не создаётся. Сохранение ограничено текущей Streamlit-сессией.

## 7. Запуск `AssistantAgent.stream_response_events()`

### 7.1. Подготовка исходного варианта

Метод сохраняет `active_before`, то есть активный UUID перед выполнением.

При обычном запросе `parent=None`. Если передан `regenerate_sequence_uuid`, он загружает исходный вариант через `get_sequence()`. При отсутствии варианта выбрасывается `ValueError`. При наличии переданный `request` заменяется на `parent.generation_request`.

Таким образом, Regenerate повторяет исходный запрос генерации выбранной последовательности. Текст последующей просьбы о замене или обмене не становится новым запросом генерации; обмен автоматически не повторяется.

### 7.2. `AssistantToolContext`: контекст одного запроса

Создаётся [AssistantToolContext](../src/langchain_app/tools/context.py), dataclass со следующими данными:

- фабрика генератора и два сервиса каталога;
- `user_request` — фактический запрос этого запуска;
- `require_generation` — обязательность генерации;
- `regeneration_parent` — исходный вариант для Regenerate;
- `generation_started=False` и `generation_completed=False` по умолчанию;
- `catalog_items_displayed=False` — один успешный показ за этот запрос, независимо от `turn_operation_committed`.

Этот объект передаётся инструментам через `runtime.context`. Модель не задаёт сервисы, URL, папку или runtime в своих аргументах.

Контекст создаётся заново на каждый вызов `stream_response_events()`. Он не является долговременным состоянием диалога. При этом его флаги доступны Python-коду в течение всего текущего выполнения.

### 7.3. `_get_agent()`: ленивое создание графа

Внутри `try` вызывается `_get_agent()`.

Если граф уже есть, метод возвращает его. Иначе импортируется `ASSISTANT_TOOLS` из [tools/__init__.py](../src/langchain_app/tools/__init__.py). Реестр содержит семь инструментов:

```text
generate_sequence
search_catalog_items
show_catalog_items
get_catalog_tag_names
replace_sequence_element
swap_sequence_elements
add_sequence_elements
```

Если `_model` — строка, создаётся модель:

```python
init_chat_model(
    self._model,
    timeout=300,
    model_kwargs={"parallel_tool_calls": False},
)
```

Таймаут модели задан в 300 секунд. `parallel_tool_calls=False` просит провайдера выдавать последовательные вызовы инструментов. Дополнительная серверная проверка параллельных пакетов всё равно есть в middleware.

Если передан готовый `BaseChatModel`, он используется напрямую. Это, в частности, позволяет тестам подставлять модель с заранее заданными ответами; настройки `init_chat_model()` в этой ветке не применяются.

Затем `create_agent()` получает:

- модель и список инструментов;
- `SYSTEM_PROMPT` с правилами поведения;
- `context_schema=AssistantToolContext`;
- `state_schema=AssistantState`;
- middleware `model_response_progress`, `selected_sequence_context`, `invalidate_catalog_candidates`, `tool_response_progress`, `sequential_tool_calls`;
- созданный ранее checkpointer.

Полученный скомпилированный граф сохраняется в `_agent`.

### 7.4. Что требует `SYSTEM_PROMPT`

Промпт требует от модели выбирать действие по намерению пользователя и передавать в генерацию полный запрос с предпочтениями и ограничениями.

Количество поз модель должна определять так:

- явно указанное число имеет приоритет, `duration_seconds` остаётся `null`;
- если есть только длительность: модель передаёт `минуты × 60` в `duration_seconds`, а предварительный `count` рассчитывает как `минуты × 60 / 40`, округление половин вверх, минимум 1;
- если нет ни количества, ни длительности — 9.

Во всех случаях `count` ограничен 45. Обычная асана занимает 40 секунд, зеркальная (`bilateral=true`) — 80 секунд за обе стороны, оставаясь одним элементом. Поэтому 10 минут дают до 15 обычных поз, меньше при зеркальных. Генератор учитывает время фактически выбранных асан. Текст запроса по-прежнему интерпретирует модель; отдельного Python-парсера длительности нет. Подробнее: [спецификация 005](specs/005-sequence-duration-and-limit/README.md).

Промпт также требует реальных данных каталога, английских поисковых условий и ответа на языке пользователя. Редактирование поддерживает замену одного элемента, обмен одной пары или добавление одного блока через TypeSafe. Ссылки разрешаются по актуальному `selected_sequence`: позиции начинаются с 1, последняя равна N, имя должно определять ровно одно вхождение. Неоднозначность, неполная пара и несколько операций требуют уточнения; отсутствие снимка и позиция вне диапазона объясняются без автоматической генерации. Вопрос о последствиях получает объяснение, а «Можешь поменять/добавить…?» выполняет однозначную команду без дополнительного подтверждения. Удаление, перемещение со сдвигом остальных элементов и ручное изменение mirroring недоступны.

Для добавления default — один элемент в конец. «До 20» означает разность 20−N, «ещё 20» — 20 новых элементов; достигнутый или меньший итоговый размер не изменяет секвенцию. Инструмент сам ограничивает блок свободным местом до 45. Добавление только по длительности требует уточнить количество. «После второй» передаёт UUID третьего вхождения, а «после последней» — null; несуществующую ссылку нельзя трактовать как конец. При нескольких местах вставки или сочетании с заменой/обменом агент уточняет одну операцию.

Показ каталога выбирается по смыслу запроса: «Покажи асаны сидя в наклоне», «Какие есть позы лежа», «Покажи ещё варианты» и «Найди кандидатов для замены/добавления, пока ничего не меняй» требуют поиска и `show_catalog_items`. Буквальное слово «покажи» и дополнительное подтверждение не нужны. Запрет изменения секвенции разрешает показ кандидатов, но запрещает генерацию, замену, обмен и добавление. Служебный поиск при генерации, замене, добавлении, вопросе о технике и запрос тегов сами по себе не разрешают галерею. Обмен не требует поиска и сам по себе не разрешает галерею. При отдельной просьбе показать каталог и выполнить операцию обе области выводятся раздельно; Generate и Regenerate исключают показ.

Наличие текста в промпте задаёт желаемое поведение модели. Проверки `count` от 1 до 45, выбранного UUID, UUID вхождений, проверенного кандидата замены и общего лимита одной успешной генерации, замены или обмена дополнительно реализованы в Python. Само намерение выполнить редактирование отдельным детерминированным классификатором здесь не проверяется.

### 7.5. Вход графа и `stream_events(version="v3")`

Вход содержит новое пользовательское сообщение и `turn_operation_committed=False`.
История восстанавливается checkpointer по `thread_id`; UI-сообщения не копируются
в граф. Regenerate дополнительно задаёт UUID родителя как активный.

```python
stream = agent.stream_events(
    inputs, context=context, config=self._config,
    version="v3", transformers=[CustomTransformer], durability="sync",
)
for event_type, data in stream.interleave("custom", "values"):
    events = progress.accept(data) if event_type == "custom" else progress.confirm_commits(data)
    for event in events:
        yield event
```

`ResponseProgress` преобразует сигналы middleware в типизированные события с
общим `request_id`, монотонным `event_index` и временем запроса. `values`
подтверждает, что новый вариант уже применён к состоянию, прежде чем публиковать
`sequence_committed` и успешное завершение соответствующего этапа. `durability="sync"`
делает подтверждённый snapshot доступным через `get_state()`.

Публичный жизненный цикл начинается с `request_started` до инициализации модели
и заканчивается `request_finished`. Финальный текст публикует model middleware,
а не разбор свободного ответа в UI. Каталожный показ не является commit секвенции.

`stream()` остаётся адаптером, выдающим прежние типы: финальный текст и
`CatalogItemSchema` из `sequence_element`. `generate()` выдаёт только эти асаны.
Оба адаптера игнорируют `catalog_items_displayed` и сохраняют поведение исключений.

## 8. Первый вызов модели и middleware

Исходник: [services/sequence_context.py](../src/langchain_app/services/sequence_context.py).

### 8.1. `selected_sequence_context()` перед каждым вызовом модели

Middleware оборачивает вызов модели. Он читает `active_sequence_uuid`, находит соответствующий snapshot в `sequences`, восстанавливает `GeneratedSequence` и вызывает `model_context()`.

`model_context()` сериализует последовательность в JSON-совместимый словарь, исключая `image_url` каждого элемента. UUID вариантов и элементов, порядок, данные асан, теги и mirror-флаги остаются.

Затем middleware добавляет к системному сообщению текст с JSON:

```json
{"selected_sequence": null}
```

либо с полным контекстом выбранного варианта.

В сопровождающем тексте указано, что этот snapshot имеет приоритет над старыми результатами инструментов. Имена и теги каталога объявлены данными. При `null` модель должна считать, что выбранной последовательности нет, и не восстанавливать её из старого текста.

При `require_generation=True` добавляется требование новой генерации.

Существующие блоки системного сообщения сохраняются; новый блок добавляется через `request.override(system_message=...)`. Он формируется заново для каждого вызова, в том числе после инструмента. Отдельные системные сообщения не накапливаются в сохранённом `state["messages"]`.

Это позволяет нажать Use this sequence на старой карточке и сразу передать модели именно её, даже если в истории есть более новые snapshots.

### 8.2. Модель возвращает ответ или вызов инструмента

Если инструмент не нужен, модель возвращает текстовый `AIMessage`; `model_response_progress` публикует его как `AssistantMessageEvent(purpose="final")`. Текст при tool call считается промежуточным и остаётся в блоке выполнения.

Если нужно действие, модель возвращает `AIMessage.tool_calls` с именем и аргументами. Схему аргументов библиотека получает из `@tool` и аннотаций функций. `ToolRuntime` передаётся приложением и скрыт из схемы, которую заполняет модель.

После ответа модели срабатывает `invalidate_catalog_candidates()`.

### 8.3. `invalidate_catalog_candidates()`

Middleware смотрит последнее сообщение. Если среди запрошенных инструментов есть `search_catalog_items`, он возвращает обновление `latest_catalog_items=[]`.

Это происходит ещё до исполнения поиска и проверки его аргументов. Старые кандидаты становятся недействительными даже тогда, когда новый поиск не дойдёт до HTTP из-за неверного `limit` или завершится ошибкой.

Если вызова поиска нет, middleware ничего не меняет. Поэтому найденные кандидаты могут сохраниться до следующего пользовательского сообщения, например после вопроса «Использовать эту позу?».

### 8.4. `_sequential_tool_calls()` перед инструментом

Middleware проверяет число вызовов в последнем `AIMessage`. Если их больше одного, каждый отклоняется `ToolMessage` с кодом `sequential_tool_calls_required`. Реальный обработчик не вызывается.

При единственном вызове выполняется `handler(request)`.

Назначение: следующий инструмент должен видеть уже применённый результат предыдущего. Поиск и замена, выданные одним параллельным пакетом, не должны работать на одном старом состоянии.

Теперь разберём ветку, в которой модель выбрала `generate_sequence`.

## 9. Переход в инструмент `generate_sequence`

Исходник: [tools/sequence.py](../src/langchain_app/tools/sequence.py).

### 9.1. Аргументы и проверки до начала работы

Инструмент принимает `request`, `count`, необязательные `starting_catalog_item_id`, `duration_seconds` и внедрённый `runtime`.

`request` имеет минимальную длину 1, а `count` должен быть строгим целым числом от 1 до 45. Значения вроде `0`, 46, отрицательного числа, строки с числом или boolean не удовлетворяют схеме `count`. Длительность должна быть положительным конечным числом секунд или `null`. Валидация схемы выполняется инструментальной инфраструктурой до тела функции.

Внутри дополнительно проверяется `request.strip()`: строка из одних пробелов возвращает ошибку `invalid_arguments` через `tool_error()`.

`tool_error()` создаёт `ToolMessage` с `status="error"`, JSON-полями `status`, `code`, `message` и ID текущего вызова инструмента. Этот ответ предназначен модели, которая сможет объяснить ошибку или исправить запрос.

Затем проверяются:

```python
context.generation_started
runtime.state.get("turn_operation_committed", False)
```

Если генерация уже начиналась или изменение уже сохранено, инструмент возвращает `operation_already_started`. Это блокирует повторную генерацию в том же запуске, а также генерацию после успешной замены, обмена или добавления.

При разрешённом запуске выставляется `generation_started=True`. Он устанавливается до обращения к генератору, поэтому повторный запуск в том же контексте не должен начаться даже после неуспешной попытки, дошедшей до этой строки.

### 9.2. Вызов сервиса и передача прогресса

`context.generator_factory()` возвращает подготовленный `SequenceGenerator`.

Инструмент начинает перебирать:

```python
generator.generate(
    request, language="en", count=count,
    starting_catalog_item_id=starting_catalog_item_id,
    **({"duration_seconds": duration_seconds} if duration_seconds is not None else {}),
    progress_observer=runtime.stream_writer,
)
```

Здесь `request` — аргумент, сформированный моделью. Инструкции требуют сохранить в нём все предпочтения пользователя. Сам сервис не сверяет его семантически с исходным сообщением.

Для каждой полученной асаны инструмент:

1. Проверяет лимит 45 элементов и добавляет глубокую копию в локальный список `items`.
2. Вызывает `runtime.stream_writer(item)`.

Tool middleware перехватывает вторую строку и публикует `SequenceElementEvent` и счётчик этапа генерации. Через `progress_observer` внутренний поиск генератора получает дочерний этап. События поступают сразу, до завершения всего инструмента. Первая сохраняет полные данные для будущего snapshot. Глубокая копия отделяет историю от возможных последующих изменений исходного объекта.

Пока цикл не закончен, инструмент ещё не возвращал `Command`, поэтому новый вариант не внесён в `state["sequences"]`.

Переходим внутрь `SequenceGenerator.generate()`.

## 10. Внутри `SequenceGenerator.generate()`

Исходник: [services/sequence_generator.py](../src/langchain_app/services/sequence_generator.py).

Константы алгоритма:

```python
STARTING_TAG = "Other/Starting"
FINISHING_TAG = "Other/Finishing"
BATCH_SIZE = 10
MAX_SEQUENCE_ELEMENTS = 45
POSE_DURATION_SECONDS = 40
```

### 10.1. Проверка количества

`count < 0` и `count > 45` вызывают `ValueError`. Без длительности `count == 0` завершает генератор без обращений к сервисам. Это поведение самостоятельного сервиса; через инструмент `generate_sequence` ноль не пройдёт валидацию аргументов.

При переданной длительности генератор проверяет её положительность и конечность, округляет бюджет до ближайшего числа 40-секундных единиц (половины вверх, минимум одна) и сам вычисляет верхний предел `count`, не превышающий 45. Каждая выбранная обычная асана расходует одну единицу, зеркальная — две. Начальная асана также учитывается. После достижения бюджета подбор прекращается; последняя зеркальная асана может превысить округлённый бюджет на одну единицу.

Параметр `language` сохранён в интерфейсе сервиса, но внутри алгоритма не используется для переключения каталога. Язык HTTP закреплён клиентом.

### 10.2. Загрузка каталога

Сервис один раз вызывает:

```python
self._catalog_item_service.search(
    with_tags=True,
    with_rigman=False,
    limit=0,
    rand=True,
)
```

`limit=0` отключает лимит на уровне HTTP API: генератор запрашивает весь доступный набор папки. Это внутренний вызов сервиса, поэтому ограничение инструмента поиска до 50 результатов к нему не относится.

`rand=True` запрашивает случайный порядок/набор по контракту каталога. После получения полного набора алгоритм также использует локальные `choice()` и `sample()`.

Из результата отбрасываются элементы без `image_url`. Оставшиеся сериализуются без `rigman_data` и `second_side_rigman_data`, затем валидируются как `CatalogItemSchema`.

Таким образом, подбор работает с ID, UUID, именем, bilateral, URL и тегами. Данные Rigman не участвуют в выборе.

Прежде чем идти дальше по алгоритму, проследим `search()` до HTTP и обратно в разделе 11. После этого выполнение возвращается к выбору стартовой позы.

### 10.3. Первая поза

Из загруженного списка выбираются асаны, у которых список тегов содержит точную строку `Other/Starting`.

Если подходящих асан с изображением нет, выбрасывается `ValueError`. Автоматического старта из произвольной асаны нет.

`choice(starting_items)` случайно выбирает одну стартовую асану. Она добавляется в `selected_items` и сразу выдаётся через `yield starting_item`.

На этом шаге Jev ещё не вызывался. Стартовая асана выбирается случайно по тегу; запрос пользователя не используется для её ранжирования.

`yield` возвращает управление в инструмент, который отправляет асану через `stream_writer`. Затем UI может показать первую картинку, пока оставшиеся позы ещё подбираются.

Если `count=1`, цикл следующих элементов не выполняется. Последовательность состоит только из стартовой позы, и TypeSafe не вызывается.

### 10.4. Промежуточные позы

Цикл `while len(selected_items) < count` добавляет оставшиеся элементы. При запросе по времени он также заканчивается, когда выбранные асаны исчерпали бюджет. Перед каждым выбором верхняя оценка числа элементов уменьшается с учётом оставшегося времени.

На каждой итерации строится множество ID уже выбранных асан. Из полного каталога исключаются все элементы с этими ID. Так обеспечивается отсутствие повторного выбора по числовому ID.

Если сейчас выбирается не последняя поза, из доступных случайно берётся не более 10 кандидатов:

```python
sample(available_items, min(BATCH_SIZE, len(available_items)))
```

Затем этот ограниченный набор передаётся в `TypeSafeService.choose_next_catalog_item()` вместе с уже выбранными позами, запросом и целевым количеством.

Jev оценивает только переданных кандидатов. Он не просматривает весь каталог и не запрашивает дополнительные асаны самостоятельно.

### 10.5. Последняя поза

Когда остаётся последний элемент по количеству или времени, алгоритм берёт все ещё не использованные асаны с точным тегом `Other/Finishing`. Если остаются две единицы времени и доступна зеркальная завершающая асана, она также предпочтительна: обе стороны заполняют оставшийся бюджет одним элементом.

Если таких нет, кандидаты — все оставшиеся асаны. Ограничение промежуточного пакета в 10 элементов здесь не применяется.

Из кандидатов снова выбирает `TypeSafeService`. Выбранная асана добавляется в `selected_items` и выдаётся через `yield`.

Если каталог исчерпан до нужного количества, пустой набор дойдёт до TypeSafe и завершится ошибкой. Частичный список не превращается в успешную короткую последовательность.

### 10.6. Что алгоритм проверяет и чему только отдаёт предпочтение

Код жёстко задаёт стартовый тег, исключает элементы без картинки, исключает уже выбранные ID и предпочитает финишный набор при выборе последней позы.

Чередование сгибаний и разгибаний, наличие скрутки и соответствие пожеланиям пользователя передаются Jev как правила выбора. После завершения нет отдельного прохода, который проверяет выполнение всех этих правил для всей последовательности.

Поэтому правила промпта и TypeSafe следует читать как критерии интеллектуального выбора, а проверки Python — как конкретные ограничения выполнения.

## 11. HTTP-поиск: `CatalogItemService` → `CatalogClient`

Исходники: [services/catalog_item.py](../src/langchain_app/services/catalog_item.py), [services/catalog_client.py](../src/langchain_app/services/catalog_client.py), [schemas/catalog.py](../src/langchain_app/schemas/catalog.py).

### 11.1. `CatalogClient.__init__()`

Базовый клиент используется и для асан, и для тегов.

Он проверяет, что `base_url` и `catalog_folder_uuid` не пусты после `.strip()`. UUID папки очищается от внешних пробелов и кодируется через `quote(..., safe="")`, чтобы попасть в один сегмент URL.

Формируется:

```text
<base_url>/api/public/catalog_folders/<encoded_folder_uuid>
```

У `base_url` удаляются внешние пробелы и завершающие `/`.

Если внешний `httpx.Client` не передан, клиент создаётся с таймаутом 10 секунд, а `_owns_client=True`. Если передан, сервис использует его и не считает своим.

`close()` закрывает только собственный клиент. `__enter__()` возвращает сервис, `__exit__()` вызывает `close()`. Кэшируемые зависимости здесь не оборачиваются в `with`; их клиенты переиспользуются между запросами.

### 11.2. `CatalogItemService.search()`: локальная валидация

Метод принимает фильтры имени, UUID, bilateral, тегов и параметры `with_rigman`, `with_tags`, `limit`, `rand`.

Первым действием создаётся `CatalogItemsSearchArguments`:

- неизвестные поля запрещены общей базой `ApiSchema`;
- `limit` — строгое целое `>=0`;
- boolean-параметры строгие;
- имя и UUID, если заданы, обрезаются по краям и не могут стать пустыми;
- каждый тег тоже обрезается и проверяется на непустоту;
- `None` для списка тегов преобразуется в пустой список.

Ошибка локальных аргументов возникает до HTTP-запроса.

Внутри схемы `normalize_filter()` обрабатывает поля `name` и `uuid`: оставляет `None` либо передаёт строку в `_nonblank()`. `normalize_tags()` вызывает `_nonblank()` для каждого тега. Общий `_nonblank()` делает `.strip()`, выбрасывает `ValueError` для пустого результата и возвращает очищенную строку. Поэтому пробелы нормализуются одинаково для всех текстовых фильтров.

### 11.3. Кодирование query-параметров

Из модели формируется список пар ключ–значение. `None` пропускается, boolean превращается в строки `true`/`false`, остальные значения — в строки.

Проверка идёт по `value is not None`, поэтому `bilateral=False` сохраняется как настоящий фильтр. Ноль для `limit` также не теряется.

Теги добавляются повторяющимся ключом:

```text
catalog_tag_names[]=Standing
catalog_tag_names[]=Balance
```

После этого вызывается `_get("catalog_items/search", params)`.

### 11.4. `CatalogClient._get()`

Базовый метод делает GET по URL папки и endpoint. К query-параметрам всегда добавляется `("language", "en")`.

Для генератора запрос имеет следующий смысл:

```http
GET /api/public/catalog_folders/yoga-public-v1/catalog_items/search?language=en&with_rigman=false&with_tags=true&limit=0&rand=true
```

Клиенты не добавляют авторизацию: используются публичные endpoints. Контракт API подробно описан в [public_catalog_items_search.md](public_catalog_items_search.md).

Обработка ошибок:

| Ситуация | Результат Python-клиента |
| --- | --- |
| `httpx.HTTPError` при обращении | `api_error_type` с сообщением о недоступности каталога |
| HTTP 404 | `CatalogFolderNotFoundError`, код `catalog_folder_not_found` |
| HTTP 422 | `api_error_type`, код `invalid_arguments` |
| Другой ошибочный HTTP-статус | `api_error_type`, код `catalog_api_unavailable` |
| Успешный статус | Возвращается `httpx.Response` для проверки тела |

`api_error_type` переопределяется подклассами: для асан это `CatalogItemApiError`, для тегов `CatalogTagApiError`.

### 11.5. Проверка JSON в `CatalogItemService.search()`

После `_get()` выполняются `response.json()` и `TypeAdapter(list[CatalogItemSearchResult]).validate_python(...)`.

Ожидается JSON-массив, без обёртки `data`. Каждый результат содержит обязательные ID, UUID или `null`, имя, bilateral и URL или `null`. Теги и два поля Rigman допускаются как необязательные поля схемы HTTP-результата.

Если запросили `with_tags=True`, поле `catalog_tag_names` каждого элемента должно содержать список: `None` запрещён, а `[]` допустим.

Некорректный JSON, структура или нарушение контракта тегов превращаются в `CatalogItemApiError` с кодом `invalid_api_response`.

Сам поиск сохраняет элементы без UUID и без изображения. Их пригодность зависит от дальнейшей операции: генератор отбрасывает элементы без изображения, а редактор дополнительно требует UUID для замены.

После успешной проверки `search()` возвращает список моделей. В пути генерации возвращаемся к разделу 10: формированию полного каталога, стартовой позе и циклу выбора.

## 12. Выбор следующей позы в `TypeSafeService`

Исходник: [services/type_safe.py](../src/langchain_app/services/type_safe.py).

### 12.1. Проверка позиции и кандидатов

`choose_next_catalog_item()` вычисляет `next_element_position = len(selected_items) + 1`.

Если позиция уже превышает `elements_count`, выбрасывается `ValueError`: последовательность уже заполнена.

Повторно исключаются ID ранее выбранных асан. Это дополнительная защита на уровне сервиса TypeSafe, даже если вызывающий код передал повторного кандидата.

Если кандидатов нет, выбрасывается `TypeSafeSelectionError`. Если кандидат ровно один, он возвращается сразу без обращения к классификатору: выбирать больше не из чего.

### 12.2. Закрытый набор вариантов `criteria`

При нескольких кандидатах строится `candidates_by_id`, где ключ — строковый числовой ID асаны, значение — исходный объект.

Для каждого ключа в `criteria` передаются:

- `id`;
- `name`;
- `bilateral`;
- `catalog_tag_names`.

Изображения, catalog UUID и сведения о вариантах последовательности классификатору не нужны. Ответ должен выбрать один из заранее заданных ключей.

### 12.3. Состояние задачи для Jev

В `state` передаются:

1. Полный `request`.
2. Статические правила `_RULES` и требование ровно `elements_count` поз.
3. Прогресс: целевое количество, число уже выбранных поз, следующая позиция, признак последнего элемента.
4. Уже выбранные асаны с ID, именами, bilateral и тегами.

Статические правила просят выбирать валидные асаны, избегать повторов, предпочитать чередование сгибаний и разгибаний, добавить скрутку, не ставить стартовые позы в середину и предпочитать завершающую позу в конце.

Сервис вызывает:

```python
self._classifier.invoke({
    "state": state,
    "questions": {
        "next_yoga_pose": Choice(
            instructions="Which catalog item is the best next yoga pose for the requested sequence and its rules?",
            criteria=criteria,
        ),
    },
})
```

Дальнейший транспорт TypeSafe реализован библиотекой `langchain_typesafe`, а не собственным HTTP-клиентом этого проекта. Здесь передаётся одна задача выбора; собственных повторных попыток в сервисе нет.

### 12.4. Проверка ответа

`TypeSafeError` преобразуется в `TypeSafeSelectionError("Could not select the next catalog item")`.

После успешного вызова извлекается `response.choices["next_yoga_pose"]`. Если ответа нет или `answer.choice` отсутствует в `candidates_by_id`, выбрасывается `TypeSafeSelectionError`: классификатор не может добавить неизвестную асану в результат.

При корректном выборе возвращается исходный `CatalogItemSchema` из словаря кандидатов. `SequenceGenerator` добавляет его в историю и выдаёт через `yield`; инструмент отправляет custom-событие; при следующем потреблении генератора начинается выбор следующей позы.

## 13. Сохранение полного варианта и возврат в интерфейс

### 13.1. Конец `generate_sequence`: материализация snapshot

Когда `SequenceGenerator.generate()` завершился без исключения, инструмент проверяет `items`. Пустой список возвращает `empty_sequence` и не создаёт вариант.

Затем вызывается:

```python
GeneratedSequence.from_catalog_items(
    items,
    request=context.user_request,
    parent=context.regeneration_parent,
)
```

Обратите внимание на два разных запроса: сервис подбора получил аргумент `request` инструмента, а snapshot сохраняет исходный `context.user_request`. Поэтому история сохраняет реальный пользовательский запрос этого запуска, даже если модель переформулировала аргумент инструмента.

В [schemas/generated_sequence.py](../src/langchain_app/schemas/generated_sequence.py) метод создаёт:

- новый UUID варианта;
- новый UUID семейства для первой генерации либо семейство родителя для Regenerate;
- `parent_uuid` и `operation="regenerate"`, если родитель есть;
- `generation_request` — исходный запрос семейства;
- `operation_request` — запрос этой операции;
- `name="New Sequence"`, `description=None`, `language="en"` по умолчанию;
- отдельный `GeneratedSequenceElement` для каждого места.

Элементы получают новый `element_id`, порядок начиная с 1, глубокую копию асаны и `start_mirror=end_mirror=catalog_item.bilateral`.

`elements_count` вычисляется как длина списка. Метод не удаляет повторные вхождения и элементы без картинок, если их передал другой генератор: snapshot сохраняет весь полученный результат. В штатном алгоритме генератор уже исключил асаны без картинки и повторные ID.

Инструмент не требует совпадения длины `items` с аргументом `count`: при запросе по времени зеркальные асаны уменьшают число элементов. В штатном пути количество и бюджет обеспечивает `SequenceGenerator`. Для любого подставленного генератора инструмент дополнительно блокирует выдачу 46-го элемента и не сохраняет результат, нарушивший обязательный лимит.

### 13.2. `Command(update=...)`: точка сохранения варианта

Последовательность сериализуется через `model_dump(mode="json")`. `context.generation_completed=True` устанавливается после подтверждения commit по состоянию графа, а не до применения `Command`.

Возвращается `Command` с обновлением:

```python
{
    "sequences": {sequence_uuid: snapshot},
    "active_sequence_uuid": sequence_uuid,
    "turn_operation_committed": True,
    "messages": [ToolMessage(...)],
}
```

`ToolMessage` содержит `status="ok"` и весь snapshot. Модель получает реальные асаны, а не только число или сообщение «готово».

Для `sequences` в `AssistantState` указан reducer `merge_sequences(previous, incoming)`. Он возвращает `{**previous, **incoming}`: новый snapshot добавляется по своему UUID, предыдущие варианты остаются. Массивы элементов разных вариантов не склеиваются.

После применения обновления графом вариант существует в памяти ассистента и становится активным. Это точка, относительно которой интерфейс отличает законченную операцию от уже показанного промежуточного прогресса.

### 13.3. Повторный вызов модели после инструмента

Граф снова вызывает модель. `selected_sequence_context()` уже видит новый `active_sequence_uuid` и добавляет актуальный snapshot в системный контекст.

Модель также получает результат инструмента через историю сообщений. Она может написать ответ на языке пользователя; инструкции требуют сохранять имена асан и тегов как в каталоге.

Текстовый `AIMessage` без вызовов инструментов публикуется как финальное событие.
`render_response()` обновляет зарезервированный Markdown из принятого текста.
Если генерация обязательна, завершение без подтверждённой генерации считается
ошибкой. Один текст «последовательность готова» не выполняет Generate.

### 13.4. Как UI рисует промежуточные асаны

`SequenceElementEvent` добавляет миниатюру в временный `SequenceView`, с порядком
из события. Асаны без картинки в этом промежуточном пути пропускаются.
Для `bilateral=true` сохраняются существующие mirror-скобки. Этот путь выводит
только секвенцию и никогда не создаёт `catalog_items`.

### 13.5. Подтверждённый результат независимо от текста

На `SequenceCommittedEvent` UI получает вариант через `assistant.get_sequence()`
и строит `generated_sequence_view()`. Полный snapshot содержит корректные UUID,
все элементы и mirror-флаги; отсутствующие изображения получают fallback-имя.
Замена и обмен используют этот же commit-путь без повторной выдачи отдельных поз.

### 13.6. Конец `render_response()`

Из `get_sequence_variants()` строятся проекции семейства и выбранный индекс.
Возвращаемый `ChatMessage` содержит:

```text
role, content, execution
catalog_items (только после успешного показа)
sequence, sequence_uuid
sequence_variant_uuids, sequence_variants, selected_sequence_index
sequence_request
```

`sequence_request` берётся из `generation_request` выбранного варианта либо
из текущего запроса. `catalog_items` хранит отдельный снимок именно выбранных
элементов каталога; он не зависит от последующих поисков или выбора варианта.

### 13.7. Возврат в `assistant.py` и `st.rerun()`

Новый ответ сохраняется всегда, включая ошибку и пустой текст. Regenerate
обновляет существующую карточку и сохраняет предыдущий `ExecutionSnapshot` в
`execution_history`. В `finally` освобождаются контролы, затем выполняется rerun.
Подборка из сообщения воспроизводится без модели и каталога. Новая операция
не запускается, пока пользователь снова не отправит запрос или Regenerate.

## 14. Ветка поиска, тегов и показа каталога

Эта ветка начинается в том же `AssistantAgent.stream_response_events()`, но модель выбирает инструменты из [tools/catalog.py](../src/langchain_app/tools/catalog.py).

### 14.1. `get_catalog_tag_names()` → `CatalogTagService.get_names()`

Инструмент не имеет видимых модели аргументов. Из `runtime.context` берётся сервис тегов и вызывается `get_names()`.

В [services/catalog_tag.py](../src/langchain_app/services/catalog_tag.py) метод вызывает:

```python
self._get("catalog_tags", [])
```

Базовый `CatalogClient` добавляет `language=en` и выполняет:

```http
GET /api/public/catalog_folders/<folder_uuid>/catalog_tags?language=en
```

После HTTP-проверок тело валидируется как строгий `list[str]`. Сервис не переводит, не сортирует заново и не переименовывает теги: сохраняет порядок и написание API. Некорректный ответ даёт `CatalogTagApiError` с кодом `invalid_api_response`.

Успешный инструмент возвращает:

```python
{"status": "ok", "language": "en", "tag_names": names}
```

Инструментальная инфраструктура передаёт результат модели. При `CatalogServiceError` вместо него возвращается ошибочный `ToolMessage` через `tool_error()`.

Этот вызов не меняет последовательности и не очищает `latest_catalog_items`: он только даёт модели реальные имена для последующего поиска. Контракт endpoint находится в [public_catalog_tag_names.md](public_catalog_tag_names.md).

### 14.2. `search_catalog_items()`

Модель может передать `name`, `uuid`, `bilateral`, `catalog_tag_names`, `limit`, `rand`. Здесь `limit` ограничен строгим целым от 1 до 50 включительно, по умолчанию 10.

Инструмент всегда вызывает сервис с `with_tags=True`, `with_rigman=False`. Модель не может переключить язык, HTTP-адрес или папку каталога.

По контракту поиска разные фильтры объединяются через AND, список тегов — через OR. Имя и теги ищутся по части строки без учёта регистра, UUID — по точному значению без учёта регистра. Ограниченная выдача не является ранжированием по смысловой близости.

Внутренний путь `CatalogItemService.search()` → `CatalogClient._get()` и проверка результата совпадают с разделом 11.

### 14.3. Сохранение проверенных кандидатов

Для каждой найденной асаны строится JSON-совместимый snapshot без полей Rigman. Возвращается `Command`, который одновременно:

- записывает найденный список в `latest_catalog_items`;
- добавляет `ToolMessage` с `status="ok"`, `language="en"`, `returned_count`, `limit` и `items`.

`returned_count` — размер полученной выдачи, а не общее число подходящих асан в каталоге. Пустой список — корректный успешный результат.

При `CatalogServiceError` инструмент возвращает `Command` с пустыми кандидатами и кодом исходной ошибки. При `ValueError` — с пустыми кандидатами и `invalid_arguments`.

Вместе с предварительным `invalidate_catalog_candidates()` это означает: новый поиск заменяет старый набор целиком. Неуспешный новый поиск не оставляет старые асаны пригодными для последующей замены.

### 14.4. Поиск без показа

Цепочка «теги → поиск → текст» не вызывает генератор и не создаёт галерею.
Middleware публикует обычные этапы и публичные результаты поиска. Проверенные
кандидаты остаются в `latest_catalog_items` до следующего поиска и могут
использоваться для последующей замены либо отдельного показа. Новый поиск
заменяет этот набор, но не меняет уже показанные подборки в сообщениях.

### 14.5. `show_catalog_items(catalog_item_ids)`

Инструмент принимает только непустой список положительных строгих целых ID.
Модель не передаёт имена, URL или mirror-флаги. Порядок аргументов задаёт порядок
галереи. Дубликаты, неизвестные ID и неверные данные отклоняются без события.

Tool восстанавливает `CatalogItemSchema` из `latest_catalog_items`, выбирает
нужные элементы и помещает отделённые JSON-снимки в `ToolMessage.artifact["items"]`.
Модели возвращаются `status="ok"`, `displayed_count` и выбранные ID. Флаг
`context.catalog_items_displayed=True` ограничивает успешный показ одним за
запрос; новый пользовательский запрос получает новый контекст.

Показ не меняет кандидатов, `sequences`, активный UUID и `turn_operation_committed`.
При `require_generation` или наличии родителя Regenerate инструмент возвращает
`generation_required`. Повторный показ возвращает `catalog_items_already_displayed`.
Пустой или неуспешный новый поиск очищает кандидатов, поэтому показать старые
ID после него нельзя. Отдельного endpoint, накопления истории поисков и
извлечения имён из свободного текста здесь нет.

### 14.6. Публикация события и живая галерея

`tool_response_progress` открывает этап `showing_catalog_items` с заголовком
Showing catalog items... и `tool_call_id`. Только после успешного результата
инструмента middleware проверяет его artifact и публикует
`CatalogItemsDisplayedEvent(type="catalog_items_displayed")`:

| Поле | Содержание |
| --- | --- |
| `request_id`, `event_index`, `elapsed_seconds` | Запрос, порядок и время |
| `step_id`, `tool_call_id` | Этап и вызов `show_catalog_items` |
| `items` | Непустой проверенный список `CatalogItemSchema` в выбранном порядке |

Событие выходит до `step_finished(ok)` с кратким числом показанных элементов.
`search_catalog_items`, получение тегов и внутренний поиск генератора никогда
не публикуют это событие. При ошибке аргументов завершается только этап инструмента;
модель может исправить вызов или объяснить ошибку.

UI пропускает событие через существующий фильтр и копирует элементы в сообщение.
`CatalogItemsRenderer` проецирует только URL и настоящее имя и вызывает общий
`ThumbnailRenderer`. Каталог расположен после текста, вне блока выполнения,
без кнопок, ID, метаданных, счётчика и mirror-скобок, включая bilateral-асаны.
CSS подключается единственным `SequenceRenderer.render_styles()` в точке входа;
размер, скругление, `cover`, интервалы и перенос секвенции и каталога общие.
URL и alt экранируются; при `image_url=None` выводится существующий fallback-имя.

Если следующая модель упала, уже подтверждённые тамбы остаются рядом с ошибкой
и после rerun. Успешный поиск без действия показа такого снимка не сохраняет.

## 15. Ветки замены и обмена поз

Исходники: [tools/sequence.py](../src/langchain_app/tools/sequence.py), [services/sequence_editor.py](../src/langchain_app/services/sequence_editor.py).

Обычный сценарий: пользователь просит заменить конкретную позу; модель использует выбранный snapshot, при необходимости ищет кандидатов, затем вызывает `replace_sequence_element`.

### 15.1. Аргументы инструмента

Инструмент принимает:

| Аргумент | Смысл |
| --- | --- |
| `sequence_uuid: UUID` | Конкретный выбранный вариант, который модель намерена изменить |
| `element_id: UUID` | Конкретное вхождение позы внутри последовательности |
| `replacement_catalog_item_id` | Положительный строгий числовой ID новой асаны из результатов поиска |
| `runtime` | Состояние, сервисы и сведения о текущем вызове, внедряемые приложением |

Позиция «третья поза» переводится моделью в `element_id` из актуального контекста. Имя асаны не используется как уникальный идентификатор вхождения.

### 15.2. Проверки в `replace_sequence_element()`

Проверки выполняются до вызова редактора, в следующем порядке:

1. `require_generation=True` → `generation_required`: Generate/Regenerate должны завершиться генерацией, замена их не подменяет.
2. Генерация уже начиналась или операция уже сохранена → `operation_already_started`.
3. Нет активного snapshot → `sequence_not_found`.
4. Переданный `sequence_uuid` не совпадает с активным вариантом → `stale_sequence`.

Исходный snapshot восстанавливается через `GeneratedSequence.from_snapshot()`.

Далее все `latest_catalog_items` валидируются как `CatalogItemSchema` и передаются в `replace_element()` вместе с исходной последовательностью, ID вхождения, ID кандидата и `context.user_request`.

### 15.3. Внутри `replace_element()`

Редактор сначала находит элемент с указанным `element_id`. Если его нет, выбрасывает `SequenceEditorError` с кодом `sequence_element_not_found`.

Затем находит кандидата с `replacement_catalog_item_id` в переданном списке. Если его нет, возвращается ошибка `catalog_item_not_verified`. Произвольный ID, придуманный моделью, не проходит.

После этого проверяется пригодность кандидата: нужны изображение и непустой catalog UUID. Иначе — `catalog_item_not_usable`.

Дальше `same_catalog_item()` сравнивает асаны: они считаются одинаковыми при совпадении числового ID либо при наличии одинаковых UUID без учёта регистра.

Если кандидат совпадает с текущей асаной, `replace_element()` возвращает `None`. Эта проверка выполняется после проверки наличия и пригодности кандидата.

Если кандидат совпадает с другой позой последовательности, выдаётся `duplicate_catalog_item`. Это предотвращает добавление дубликата на другое место, в том числе при одинаковом UUID и разных числовых ID.

### 15.4. Создание варианта замены

При успешных проверках редактор делает глубокую копию исходной последовательности с обновлениями:

```python
{
    "uuid": uuid4(),
    "parent_uuid": sequence.uuid,
    "operation": "replace",
    "operation_request": request,
}
```

`family_uuid` и `generation_request` наследуются. Имя, описание, язык, число элементов и порядок остаются прежними.

В копии находится то же вхождение по `element_id`, заменяется его `catalog_item`, а оба mirror-флага устанавливаются в `replacement.bilateral`.

ID вхождений сохраняются у всех элементов, включая заменённый. Это изменение асаны в существующем месте последовательности. При Regenerate, напротив, создаются новые вхождения для заново подобранного списка.

Оригинал остаётся неизменным благодаря `model_copy(deep=True)`.

### 15.5. Возврат из редактора в инструмент

`SequenceEditorError` преобразуется в `ToolMessage` с её кодом. Новый вариант не сохраняется.

Если редактор вернул `None`, инструмент выдаёт `status="no_change"` и UUID исходного варианта. `turn_operation_committed` при этом не становится `True`, активный UUID не меняется, новая карточка не создаётся.

При новом варианте возвращается `Command` с добавлением snapshot в `sequences`, новым активным UUID и `turn_operation_committed=True`.

Успешный `ToolMessage` содержит весь snapshot и блок `replacement`: ID вхождения, порядок, старую и новую асану. Модель может назвать пользователю конкретную выполненную замену.

### 15.6. Возврат в UI и дальнейшие запросы

После инструмента middleware передаёт модели новый выбранный вариант. Финальный текст идёт как `AssistantMessageEvent(purpose="final")`.

Замена не выдаёт каждую позу заново. После подтверждения состояния публикуется `SequenceCommittedEvent`; UI строит карточку из сохранённого snapshot. Служебный поиск кандидатов не создаёт каталожную галерею. Она возможна только при отдельном запросе пользователя и успешном `show_catalog_items`.

`render_response()` включает в новую карточку известные ассистенту варианты того же семейства. Предыдущие snapshots и сообщения остаются в истории.

Повторная замена, обмен или генерация после успешной замены в том же запросе блокируется флагом `turn_operation_committed`. Следующее пользовательское сообщение сбросит флаг, и новое редактирование можно выполнить в отдельном ходе.

Общий лимит одной операции относится к успешно применённым изменениям. Ошибка проверки и `no_change` не создают вариант. Просьбу выполнить несколько операций модель должна сначала уточнить по правилам системного промпта.

### 15.7. `swap_sequence_elements`: обмен выбранной пары

Модель передаёт три UUID: `sequence_uuid`, `first_element_id` и
`second_element_id`. Позиции и catalog IDs не заменяют UUID вхождений;
`runtime` внедряется приложением. Инструмент сначала проверяет
`require_generation` → `generation_required`, затем начавшуюся генерацию
или commit → `operation_already_started`, наличие полного активного снимка
→ `sequence_not_found` и совпадение UUID выбранного варианта → `stale_sequence`.
Даже сохранённый старый вариант нельзя изменить, пока он не выбран.

`swap_elements()` проверяет оба вхождения до создания копии. Неизвестный ID,
включая два одинаковых неизвестных IDs, даёт `sequence_element_not_found`.
Одинаковое существующее вхождение возвращает `None`; tool отвечает
`status=no_change` и исходным UUID без изменения состояния и расходования лимита.

Успех создаёт глубокую копию с новым UUID, прежней family, `parent_uuid`
выбранного источника, `operation=swap` и полным текущим `operation_request`.
Исходный `generation_request`, метаданные и число элементов сохраняются.
Целые вхождения меняются позициями вместе с `element_id`, полным `catalog_item`
и обоими mirror flags, затем `order` пересчитывается в `1..N`. Промежуточные
позиции не сдвигаются. Flags не пересчитываются по `bilateral`; разные вхождения
одного catalog item также можно обменять.

Один `Command` добавляет полный snapshot в `sequences`, делает его активным,
устанавливает `turn_operation_committed=True` и добавляет `ToolMessage`.
Помимо `status=ok` и полного снимка, результат содержит две записи `swap`
в порядке аргументов: `element_id`, `old_order`, `new_order`. Следующий вызов
модели видит новый выбранный снимок и кратко называет позы и позиции на языке
пользователя. Каталог, генератор, tags service и TypeSafe не вызываются;
`latest_catalog_items` не меняется. Правила генерации стартовой, второй
и завершающей позы явно запрошенный обмен не ограничивают.

### 15.8. Прогресс и карточка обмена

Этап `updating_sequence` называется `Swapping sequence elements...`.
После подтверждения полного snapshot в state выходит один `sequence_committed`,
затем этап завершается с `Sequence elements swapped.`. Ошибка и `no_change`
завершают этап без commit; `no_change` сообщает об одном и том же вхождении.
Обмен не выдаёт предварительные `sequence_element` и каталожную галерею.

UI строит обычную карточку из нового снимка, с историей family, Previous/Next,
Use this sequence, Regenerate и Save. Save получает новый `info.uuid`,
catalog UUIDs, обменённый порядок и сохранённые flags; повторный Save сохраняет
UUID варианта. Rerun восстанавливает карточку и прогресс без вызова tools,
а ошибка финального текста после commit сохраняет вариант и Save.
Regenerate использует первоначальный `generation_request`, создаёт вариант
`regenerate` и автоматически обмен не повторяет. Подробный контракт:
[фича 006](specs/006-swap-sequence-elements/README.md).

### 15.8. `add_sequence_elements`: один блок новых элементов

Модель передаёт UUID выбранного снимка, строго положительное целое `count`,
полный запрос с пожеланиями и необязательный UUID вхождения, перед которым
вставляется блок. Null означает конец. `count` — число новых элементов,
без верхней границы в схеме; фактическое K вычисляет инструмент по свободному месту.

До генератора проверяются `require_generation`, общий лимит операций, полный
активный snapshot, его UUID, непустой request/source и якорь. Неизвестный якорь
отклоняется даже при достигнутом лимите. При N≥45 возвращается `no_change`
с `sequence_limit_reached`, исходным UUID, `added_count=0` и `limit_applied=true`.
Иначе K=min(count, 45−N); фактическая длина берётся из `elements`.

`SequenceGenerator.add_elements` использует общие загрузку каталога и фильтры
с генерацией. Сервис проверяет K и якорь самостоятельно, до сети; он не создаёт
историю и не меняет source. `TypeSafeService.choose_addition_catalog_item`
передаёт Jev исходный и текущий запросы, полный фиксированный prefix/suffix,
исходные позиции и mirror flags, выбранные добавления и счётчики. Image URLs
и rigman исключены. Новый старт при prepend выбирается TypeSafe, без случайного
распределения генерации. Жёсткие правила новых стартовых поз и изменённой
первой/второй пары проверяются до выбора; предпочтения оценивают весь результат.
Последняя новая поза считается финишем только при пустом suffix.

`insert_elements` повторно валидирует весь блок: ровно K пригодных items,
catalog UUIDs, миниатюры, отсутствие новых повторов по ID/UUID, лимит и жёсткие
правила. Невалидный результат даёт `invalid_addition_result`; ошибка каталога —
`catalog_search_failed`, ошибка выбора или некорректный ответ TypeSafe —
`addition_selection_failed`. Частичного commit нет.

Редактор создаёт глубокую копию с новым UUID, `operation=add`, parent выбранного
варианта и текущим `operation_request`. Family, `generation_request` и метаданные
наследуются. Исходные вхождения и flags сохранены; новые IDs уникальны,
оба новых flags равны `bilateral`, весь порядок пересчитывается от 1.
Один `Command` фиксирует полный snapshot, активный UUID и общий флаг операции.
`ToolMessage.addition` содержит requested/added counts, limit_applied, начальную
позицию блока, якорь и новые element IDs/orders. Внутренний каталог не читает
и не меняет `latest_catalog_items`.

Middleware показывает `updating_sequence` с заголовком
`Adding sequence elements...`; `GeneratorSearchProgress` создаёт настоящий
дочерний поиск. `GeneratorAdditionProgress` передаёт completed=0..K, total=K.
Предварительных `sequence_element` и отдельной галереи нет. После доступности
полного состояния `PendingSequenceCommit` подтверждает ровно один commit,
затем завершает этап с количеством добавленных элементов и ограничением,
если оно применено. Ошибка/no_change не создают карточку.

Существующая карточка поддерживает историю, выбор старого parent, Save и rerun.
Ошибка финального текста после commit оставляет результат доступным.
Regenerate использует исходный `generation_request` без повторения добавления.
Контракт и результаты приёмки: [фича 007](specs/007-add-sequence-elements/README.md).

## 16. Previous, Next, Use this sequence и Regenerate

Эти действия обрабатываются в `_render_message_sequence()` во время восстановления истории, то есть до проверки нового текста внизу `assistant.py`.

### 16.1. Выбор активного варианта: `select_sequence()`

`AssistantAgent.select_sequence(uuid)` сначала проверяет наличие варианта через `get_sequence()`. Для неизвестного UUID выбрасывается `ValueError`.

Затем вызывается:

```python
self._get_agent().update_state(
    self._config,
    {"active_sequence_uuid": sequence_uuid},
)
```

Это обновляет состояние графа без вызова модели и инструментов. Сами snapshots не переписываются.

В текущем приложении активный вариант один на ассистента. У каждой карточки свой индекс показанного варианта; отображаемая старая карточка не должна автоматически менять глобальный активный выбор только из-за того, что её заново нарисовали.

### 16.2. Use this sequence

Если у карточки есть полный snapshot и её UUID совпадает с `active_sequence_uuid`, показывается Active sequence.

Если UUID отличается, отображается Use this sequence. Нажатие вызывает `select_sequence()` и `st.rerun()`.

Последующий вопрос, например «Что у меня третье?», получит в системном контексте именно выбранный вариант.

### 16.3. Previous Sequence и Next Sequence

Кнопки появляются при нескольких вариантах. Previous уменьшает индекс, Next увеличивает; на границах соответствующая кнопка отключена.

При изменении индекса метод обновляет `selected_sequence_index`, `sequence` и `sequence_uuid` в сообщении. Если доступен полноценный ассистент, новый UUID также выбирается через `select_sequence()`. Затем выполняется rerun.

Навигация не обращается к каталогу, Jev или языковой модели. Кнопка Save использует вариант, выбранный в этой карточке.

### 16.4. Нажатие Regenerate

Кнопка отключена во время другого запроса или если исходный запрос недоступен.
Callback `enqueue_regeneration()` ставит `PendingResponse` с `require_generation=True`,
UUID источника и индексом сообщения. Основной цикл точки входа использует тот же
`render_response()` и поток событий, что чат и Generate. Отдельного старого
`render_generated_sequence()` больше нет.

Успешная попытка обновляет выбранную карточку. Неуспешная сохраняет прежний
вариант и публичную историю попытки. Regenerate не создаёт и не очищает
`catalog_items` уже существующего сообщения.

### 16.5. `AssistantAgent.generate()` как адаптер

`generate()` остаётся совместимым API: потребляет `stream()` с обязательной
генерацией и выдаёт только `CatalogItemSchema`. `stream()` преобразует
`stream_response_events()` в прежние объекты асан и финальный текст.
Каталожный показ эти адаптеры не выдают. Основной UI использует события напрямую.
Аргумент `language` сохранён для совместимости; каталог остаётся английским.
При UUID источника используются его `generation_request` и семейство, независимо
от нового dropdown. В контексте Generate / Regenerate `show_catalog_items` запрещён.

### 16.6. Успех и ошибка Regenerate

После успешной генерации `GeneratedSequence.from_catalog_items()` создаёт новый UUID, прежний `family_uuid`, `parent_uuid` выбранного источника и `operation="regenerate"`. Старые элементы не копируются как места: у новых элементов новые `element_id`.

Карточка дополняет свой список `sequence_variants` новым представлением, выбирает его, обновляет `sequence_uuid` и, при наличии списка UUID, добавляет новый UUID туда. Затем запускается rerun.

UI-карточки хранят свои списки UUID. Восстановление карточки перечитывает snapshots именно по этому списку; оно не добавляет автоматически все будущие варианты семейства в каждую старую карточку. Все полные варианты при этом хранятся в графе, а новая карточка ответа получает семейство через `get_sequence_variants()`.

Если генерация прервалась до завершения, новый вариант не добавляется. `stream_response_events()` восстанавливает `active_before`, если временно переключал активный контекст на родителя Regenerate. Это важно при неудачной регенерации старой карточки, когда до нажатия был выбран другой вариант.

Для legacy-карточки без полного snapshot передаётся `sequence_uuid=None`. Генерация может использовать восстановленный текст запроса, но у неё нет сохранённого родителя для привязки к старому семейству.

## 17. Save: передача в Asana Catalog через браузер

Исходник: [ui/sequence_import.py](../src/langchain_app/ui/sequence_import.py). Полный контракт внешней стороны: [import_generated.md](import_generated.md).

### 17.1. Python регистрирует компонент

`render_sequence_import(sequence, catalog_url, key)` вызывает `_save_component()`, который регистрирует компонент `st.components.v2.component("asana_catalog_sequence_import", ...)`.

Компонент получает:

```python
data={"sequence": sequence, "catalog_url": catalog_url}
```

HTML содержит кнопку Save и область статуса, CSS задаёт оформление, JavaScript реализует обмен между окнами.

При отображении компонента запись в Asana Catalog ещё не выполняется. Дальше работа идёт в браузере после клика, без Python-инструмента агента.

### 17.2. Клик: открытие страницы импорта

JavaScript находит кнопку и статус в `parentElement`, устанавливает `onclick` и функцию очистки обработчиков.

При клике сначала выполняется предыдущий `cleanup()`. Затем:

1. Из `data.catalog_url` берётся origin — протокол, хост и порт.
2. Строится URL `/sequences/import` на этом origin.
3. Добавляется query-параметр `origin=window.location.origin`, то есть адрес источника.
4. Синхронно в обработчике клика вызывается `window.open(..., "_blank")`.

Если браузер заблокировал новое окно, показывается сообщение о разрешении всплывающих окон.

Если окно открылось, Save временно отключается, а статус предлагает дождаться Asana Catalog и при необходимости войти в аккаунт в новой вкладке.

### 17.3. Проверка входящих сообщений

Компонент слушает `window.message`. Сообщение обрабатывается только при одновременном совпадении:

```javascript
event.origin === catalogOrigin
event.source === receiver
```

То есть ответ должен прийти с нужного origin и именно из открытого окна.

Поддерживаются три события:

| Событие | Действие генератора |
| --- | --- |
| `asana-catalog:sequence-import:ready` | Передаёт в окно `{type: "asana-catalog:sequence-import:save", sequence: data.sequence}` через `postMessage` с конкретным `catalogOrigin` |
| `asana-catalog:sequence-import:saved` | Показывает подтверждение, удаляет обработчик и таймер, снова включает Save |
| `asana-catalog:sequence-import:error` | Показывает ошибку и продолжает слушать ответы для повторной попытки на странице импорта |

JSON последовательности не помещается в query string. Ключи доступа каталога не передаются Python-приложению генератора этим механизмом.

### 17.4. Таймер и очистка

Раз в секунду таймер проверяет `receiver.closed`. Если вкладка закрыта до подтверждения сохранения, выводится соответствующий статус и выполняется `cleanup()`.

`cleanup()` удаляет listener, очищает interval и включает кнопку. При удалении компонента из страницы также вызывается cleanup и сбрасывается `button.onclick`.

Общий таймаут ожидания открытой вкладки не задан. После события `error` компонент сохраняет listener; повторную попытку должен выполнить интерфейс импорта.

### 17.5. Что происходит на стороне Asana Catalog

В этом репозитории реализована передача, а серверный импорт находится в другом приложении. По [описанному контракту](import_generated.md) страница импорта использует авторизацию текущего пользователя каталога, отправляет JSON в `POST /api/sequences/import_generated`, затем открывает сохранённую последовательность.

Каталог должен разрешать origin генератора через `SEQUENCE_GENERATOR_ORIGINS`. Это настройка внешнего сервера, не поле `AssistantToolContext`.

По контракту `info.uuid` — идентификатор сохраняемого варианта, а `thumbnails[].uuid` — UUID асан каталога. Повторное сохранение того же UUID тем же пользователем возвращает существующую запись; новая генерация или замена получает новый UUID. Импорт принимает от 1 до 75 элементов; отдельный обязательный предел генерации — 45 элементов.

Генератор передаёт UI-проекцию выбранного варианта, а не внутренний LangGraph-state. В ней нет `family_uuid`, `parent_uuid` и `element_id`: они нужны локальной истории агента. Результат Save отображается в компоненте; Python-код не заменяет локальный `info.id=0` числовым ID созданной записи.

## 18. Состояние, схемы и идентификаторы

### 18.1. Три области хранения

| Область | Что содержит | Срок жизни |
| --- | --- | --- |
| `st.session_state` | UI-сообщения, объект ассистента, значения виджетов, временное заполнение prompt | Текущая Streamlit-сессия, включая её обычные rerun |
| `AssistantAgent` + `InMemorySaver` | История сообщений модели, полные snapshots, активный UUID, последние кандидаты, флаг операции | Жизнь экземпляра ассистента в памяти процесса |
| `st.cache_resource` | HTTP-клиенты, TypeSafeService, SequenceGenerator | Кэш процесса; при одинаковых аргументах ресурсы переиспользуются |

Базы данных или файлового хранилища диалога этот путь не использует. Перезапуск процесса уничтожает in-memory checkpoints. Новая сессия не восстанавливает старую историю автоматически. Сохранение в Asana Catalog — отдельное пользовательское действие.

### 18.2. `AssistantState` и `AssistantInputState`

В [schemas/assistant.py](../src/langchain_app/schemas/assistant.py) состояние расширяет библиотечный `AgentState`:

| Поле | Назначение |
| --- | --- |
| `messages` | История user/AI/tool-сообщений, унаследованная от `AgentState` |
| `sequences` | Словарь полных вариантов по UUID; объединяется `merge_sequences()` |
| `active_sequence_uuid` | Единственный текущий выбранный вариант либо `None` |
| `latest_catalog_items` | Кандидаты из последнего поиска для проверяемой замены и явного показа |
| `turn_operation_committed` | Признак успешного изменения последовательности в текущем запросе |

`AssistantInputState` разрешает на входе `active_sequence_uuid` и `turn_operation_committed`, помимо библиотечных полей. Это позволяет запуску явно сбросить флаг операции и временно выбрать родителя Regenerate.

Поля `NotRequired` могут отсутствовать до первой записи. Поэтому код читает их через `.get()` с подходящим значением по умолчанию.

`AssistantToolContext` хранит зависимости и флаги текущего запуска отдельно от этого состояния. HTTP-клиенты не сериализуются внутрь snapshots.

### 18.3. Четыре разных идентификатора

| Идентификатор | Что идентифицирует | Где используется |
| --- | --- | --- |
| `GeneratedSequence.uuid` | Один завершённый вариант | Ключ `sequences`, активный выбор, Regenerate, Save |
| `family_uuid` | Семейство исходной генерации и её вариантов | История Previous/Next и `get_sequence_variants()` |
| `GeneratedSequenceElement.element_id` | Одно вхождение внутри варианта; при обмене следует за позой | Однозначная замена или обмен элементов |
| `catalog_item.id` и `catalog_item.uuid` | Асана внешнего каталога | ID для поиска/проверки замены; UUID для импорта |

`parent_uuid` связывает новый вариант с конкретным источником. Семейство может ветвиться: замена, обмен или Regenerate старого варианта создаёт нового потомка именно этого варианта.

`order` определяет порядок поз, но не заменяет `element_id`. Два вхождения одной и той же асаны в общем формате snapshot могут иметь разные IDs вхождений.

### 18.4. Схемы данных

Общая [ApiSchema](../src/langchain_app/schemas/base.py) использует `extra="forbid"`: неизвестные поля в этих Pydantic-моделях вызывают ошибку. Это запрет лишних полей, а не глобальное включение строгого режима для всех типов. Строгость конкретных аргументов задаётся отдельно через `Field(strict=True)`.

Основные схемы:

| Схема | Назначение |
| --- | --- |
| `CatalogItemSearchResult` | Ответ HTTP с необязательными тегами/Rigman-полями |
| `CatalogItemSchema` | Полная рабочая асана с обязательным списком тегов |
| `CatalogItemsSearchArguments` | Проверенные параметры HTTP-поиска |
| `GeneratedSequenceElement` | Вхождение асаны, порядок и mirror-флаги |
| `GeneratedSequence` | Завершённый вариант, семейство, происхождение и элементы |
| `ChatMessage` | Типизированный словарь текста, `execution`, необязательного `catalog_items` и карточек секвенции |
| `CatalogItemsDisplayedEvent` | Подтверждённый снимок выбранных элементов, связанный с этапом показа |
| `ExecutionSnapshot` | Публичная история этапов и исход запроса для rerun |
| `SequenceInfo`, `AsanaThumbnail`, `SequenceView` | Типизированные словари для отображения и импорта |

`model_dump(mode="json")` приводит UUID и URL к JSON-совместимым значениям. Восстановление через `model_validate()` снова проверяет данные схемой.

## 19. Ошибки и границы восстановления

### 19.1. Ожидаемая ошибка инструмента

Ошибка поиска, неподходящий кандидат или устаревший UUID обычно возвращаются модели как `ToolMessage(status="error")`. Граф может продолжить работу: модель объяснит проблему, задаст вопрос или исправит следующий вызов.

Ошибка не равна пустому успешному результату. Например, `items=[]` со статусом `ok` означает, что поиск выполнился и ничего не нашёл; `invalid_api_response` означает нарушение контракта ответа.

Ошибки схем аргументов обрабатывает инструментальная инфраструктура. Они возникают раньше тела инструмента; предварительное middleware очистки кандидатов учитывает и этот случай.

### 19.2. Исключение во время исполнения графа

Общий `except Exception` в `AssistantAgent.stream_response_events()` сначала подтверждает применённые commits из состояния графа, затем вызывает `_complete_failed_tool_calls()`.

Метод читает сохранённую историю в обратном порядке, собирает ID уже отвеченных `ToolMessage` и находит последнее `AIMessage`. Для его вызовов без ответа создаются ошибочные сообщения:

```json
{"status": "error", "code": "tool_execution_failed"}
```

Они дописываются через `update_state(..., as_node="tools")`.

Это восстанавливает связность истории «вызов инструмента → ответ инструмента» после исключения, например когда генератор успел показать одну позу и упал. Следующий пользовательский запрос не должен отправлять модели незакрытый tool call.

Метод не повторяет упавший инструмент и не достраивает частичную последовательность.

После этого при неудачном Regenerate, если генерация не завершена, восстанавливается прежний активный UUID.

После этого публикуется `request_finished(error)` с публичной ошибкой. `OpenAIError` и `GraphRecursionError` оборачиваются в `AssistantAgentError("Language model request failed: ...")`. Остальные исключения пробрасываются дальше без этого преобразования.

Текст публичной ошибки выбирает `services/request_errors.py` по полям исключения
OpenAI SDK, в том числе через цепочку причин. Для HTTP 429 с
`code=credit_balance_exhausted` пользователь видит сообщение об исчерпании
API-кредитов и ссылку на пополнение. Общий `insufficient_quota` предлагает
проверить баланс и лимиты; другие причины используют прежнее общее сообщение.
Текст исключения не участвует в распознавании и не попадает в публичную историю.
Подробнее: [фича 008](specs/008-api-credit-errors/README.md).

### 19.3. Что перехватывает рендерер

`render_response()` ловит `Exception` вокруг создания зависимостей и потребления
событий. Если producer не успел завершить поток, `ResponseExecution.fail()`
создаёт терминальный результат и закрывает незавершённые этапы. `progress.finish()`
выводит публичную ошибку без приватного текста исключения.

При ошибке до терминального события рендерер передаёт в `fail(error_message=...)`
сообщение из того же классификатора. Уже завершённый producer результат не
перезаписывается. Alert и replay после rerun используют сохранённое
`ExecutionSnapshot.error_message`.

Временные позы без commit удаляются; завершённая секвенция и уже подтверждённая
каталожная подборка сохраняются в `ChatMessage` вместе с `execution` даже при
пустом тексте. Галерея не появляется из одного успешного поиска. Rerun показывает
сохранённую ошибку и снимки без повторного запроса к внешним сервисам.

### 19.4. Разница между частичным прогрессом и завершённой операцией

| Момент сбоя | Что остаётся |
| --- | --- |
| До получения первой асаны | Нового варианта нет; прежний выбранный вариант сохраняется |
| После нескольких custom-асан, до окончания генератора | Картинки могли появиться в текущем проходе, но новый snapshot и карточка в истории не сохраняются |
| После применения `Command` генерации, во время финального ответа модели | Завершённый новый вариант остаётся и может быть добавлен в UI-историю |
| Во время проверки замены или обмена | Исходный вариант сохраняется без изменений |
| После применения `Command` замены или обмена, во время финального ответа модели | Новый вариант остаётся доступен для выбора и Save |
| После успешного поиска, до show_catalog_items | Галереи и catalog_items нет |
| После успешного show_catalog_items, во время финального текста | Проверенная подборка остаётся в сообщении вместе с ошибкой |
| Во время Save | Локальный вариант остаётся в памяти; результат внешнего сохранения отображается компонентом |

Сохранение snapshot здесь означает запись состояния графа в память, а не транзакцию базы данных и не запись в Asana Catalog.

### 19.5. Текущие ограничения реализации

История сообщений и snapshots не обрезается кодом приложения. Нет восстановления после перезапуска, фоновой очереди задач, отдельного механизма отмены пользователем или собственного цикла повторных попыток в сервисах. Возможные внутренние retries библиотек определяются их настройками.

Поддерживается замена одного элемента, обмен одной пары или добавление одного блока за запрос, с общим лимитом одной успешной генерации или правки. Удаление, перемещение одного элемента со сдвигом остальных и самостоятельное изменение mirror-флагов не представлены отдельными инструментами.

Определение намерения, перевод поисковых слов, определение длительности и выбор действия делегированы модели. Программные проверки защищают состояние от конкретных неверных вызовов, но не проверяют все смысловые условия пользовательского запроса.

## 20. Вспомогательные пути и карта исходников

### 20.1. `get_sequence_view()` и публичная готовая последовательность

В [ui/sequence.py](../src/langchain_app/ui/sequence.py) также есть `get_sequence_view(base_url, sequence_id, language)`. Она кэширует результат через `st.cache_data(ttl=300)`, то есть до пяти минут.

В текущем пути `assistant.py` эта функция не вызывается. Она нужна для отображения уже существующих публичных последовательностей в других потребителях UI-модуля.

Внутри:

```text
get_sequence_view()
  → with SequenceService(base_url) as service
    → service.get_by_id(sequence_id, language=language)
      → get_sequence(...)
        → _validate_lookup(...)
        → HTTP GET
        → SequenceSchema.model_validate(...)
  → преобразование в info/thumbnails
```

### 20.2. `SequenceService`: проход по методам

В [services/sequence.py](../src/langchain_app/services/sequence.py) конструктор проверяет непустой адрес, сохраняет его без завершающего `/`, создаёт либо принимает HTTP-клиент с таймаутом 10 секунд и запоминает владельца клиента.

`get_by_id()` и `get_by_name()` — короткие адаптеры к `get_sequence()`.

`_validate_lookup()` требует:

- ровно одно из `sequence_id` или `name`;
- положительный ID, который не является boolean;
- непустое после `.strip()` имя;
- язык из `en`, `uk`, `ru`.

Имя проверяется на непустоту, но в HTTP передаётся исходное значение. По контракту это поиск по точному имени/переводу, в отличие от поиска части имени асаны.

`get_sequence()` делает GET `/api/public/sequences/<id>` либо GET `/api/public/sequences?name=...`, добавляя `language`.

Сетевая ошибка превращается в `SequenceApiError`; 404 — в `SequenceNotFoundError`; 422 — в `SequenceValidationError`; другой ошибочный статус — в `SequenceApiError`.

Для 422 `_error_message()` пробует прочитать JSON и найти строковое `message`, `error` либо `detail`. Если это невозможно, возвращает общее сообщение. При успешном ответе тело валидируется как `SequenceSchema`.

`SequenceSchema` содержит ID, имя, slug, описание, язык, количество и список `SequenceElementSchema`; у элемента есть UUID, порядок, mirror-флаги, признак дыхательного режима и необязательный `catalog_item`.

`__exit__()` вызывает `close()`, который закрывает собственный клиент. Переданный извне клиент не закрывается.

Вернувшись в `get_sequence_view()`, функция формирует `info` с числовым ID и `uuid=None`, а в миниатюры включает только элементы, у которых есть асана и изображение. Это отдельный путь чтения публичной последовательности, не источник редактируемого snapshot агента.

Контракт описан в [public_sequences.md](public_sequences.md).

### 20.3. `get_thumbnails_one_by_one()`

Функция перебирает готовые миниатюры, выполняет `time.sleep(delay_seconds)` и выдаёт очередную. Значение по умолчанию — 0,05 секунды.

В основном `SequenceRenderer._render_images()` её не вызывает: он напрямую потребляет `thumbnails`. Поэтому основной путь генерации не добавляет искусственную паузу 0,05 секунды на каждую картинку. Постепенное появление связано с реальным поступлением асан от инструмента.

### 20.4. Остальные точки входа

`chat.py`, `langchain-training/`, `streamlit-training/` и `typesafe-training/` содержат отдельные примеры. `assistant.py` не вызывает их как этапы обработки запроса.

Команда `uv run langchain-app` использует другой entrypoint из `[project.scripts]`. Для описанного сервера нужна команда Streamlit из раздела 1.

Общие понятия библиотек сверены с официальной документацией:

- [Streamlit Session State](https://docs.streamlit.io/develop/concepts/architecture/session-state): повторное исполнение скрипта и сохранение значений внутри сессии.
- [Streamlit `st.cache_resource`](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.cache_resource): переиспользование ресурсных объектов между rerun и сессиями при стандартной области кэша.
- [LangChain Event streaming](https://docs.langchain.com/oss/python/langchain/event-streaming): `stream_events(version="v3")`, проекции, сырые события и совместное потребление через `interleave()`.
- [LangGraph Event streaming](https://docs.langchain.com/oss/python/langgraph/event-streaming): формат событий и подключение необходимых режимов через трансформеры.

Конкретные настройки, порядок проверок, алгоритм выбора и форматы состояния в этом документе взяты из исходников проекта. Документация библиотек объясняет механизм, но не заменяет код текущей реализации.
