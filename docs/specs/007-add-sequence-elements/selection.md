# 007 — Подбор добавляемых элементов через TypeSafe

Связанные документы: [контракт фичи](README.md), [приёмка](acceptance.md).

## 1. Общий механизм

Сейчас `SequenceGenerator.generate` загружает каталог, выбирает стартовую позу
и вызывает `TypeSafeService.choose_next_catalog_item` для продолжения списка.
TypeSafe выбирает один catalog item через `Choice`; код задаёт кандидатов,
исключает повторы и управляет последовательностью шагов.

Добавление расширяет этот же механизм контекстом вставки. Выделить общие
загрузку пригодных catalog items, построение кандидатов, правила и вызов
TypeSafe. Существующий `choose_next_catalog_item` может остаться адаптером
обычной генерации, а новый режим — адаптером вставки к общему выбору.
Существующие публичные вызовы `generate` и `choose_next_catalog_item` сохраняются.
Параллельные реализации правил и отдельный TypeSafe-клиент для добавления
не допускаются: изменения общих правил должны доходить до обоих режимов.

Код вычисляет количество и позиции, проверяет UUID и лимиты и фиксирует
результат. TypeSafe оценивает, какая из доступных асан лучше соответствует
месту в секвенции и запросу. `Choice` возвращает выбор из заданного набора,
а структурированный `state` несёт контекст этого выбора. См. актуальные
[Choice](https://docs.typesafe.ai/primitives/choice) и
[State](https://docs.typesafe.ai/concepts/state).
Пример разделения получения кандидатов и семантического выбора есть в
[cookbook по ранжированию](https://docs.typesafe.ai/cookbooks/rerank_typesafe);
для этой фичи сохраняется существующий Choice, без перехода на другой primitive.

Новые items выбираются последовательно: выбор следующего зависит от предыдущих.
Нельзя выбрать K асан независимыми вопросами на одном неизменном state:
так они не увидят уже выбранные добавления. При единственном пригодном кандидате
разрешён существующий shortcut без обращения к модели; все проверки сохраняются.

## 2. Контекст вставки

Обозначения: N — исходный размер, K — фактический размер нового блока,
p — позиция начала вставки в диапазоне `1..N+1`, j — шаг выбора `1..K`.

Для исходного списка `[A, B, C, D]`, места 3 и K=2 зафиксировать:

```text
fixed_prefix = [A, B]
fixed_suffix = [C, D]
selected_additions = [] → [X] → [X, Y]
result = fixed_prefix + selected_additions + fixed_suffix
```

На каждом шаге TypeSafe получает:

| Поле state | Содержание |
| --- | --- |
| `mode` | `add` |
| `generation_request` | Первоначальный запрос генерации; контекст практики |
| `request` | Полный текущий запрос на добавление; приоритет для новых элементов |
| `rules` | Общие правила с явным указанием неизменяемости исходных вхождений |
| `sequence_progress` | Исходный размер N, размер блока K, итоговый размер N+K, число выбранных новых items, актуальная позиция выбора |
| `fixed_prefix` | Все исходные элементы перед местом вставки |
| `selected_additions` | Уже выбранные новые items в порядке вставки |
| `fixed_suffix` | Все исходные элементы после места вставки |

В `sequence_progress` явно задать `original_elements_count=N`,
`added_elements_count=K`, `elements_count=N+K`, `selected_additions_count=j-1`,
`remaining_additions_count=K-j+1`, `next_element_position=p+j-1`,
`is_selecting_last_added_element=(j==K)` и
`is_selecting_last_element=(p+j-1==N+K)`.
Значение `selected_additions_count` не включает фиксированные исходные элементы.

Для исходных элементов передаются `element_id`, позиции, catalog ID/UUID,
имена, теги, `bilateral` и фактические mirror flags. Для выбранных новых items —
catalog ID/UUID, имена, теги и `bilateral`; flags новых вхождений будут равны
`bilateral`. Image URLs и rigman-данные не нужны в запросе к TypeSafe.
Исходные позиции явно обозначены как исходные: позиции хвоста в результате
сдвигаются на K. Актуальная позиция кандидата на шаге j — `p + j - 1`.

`sequence_progress` различает «последняя асана добавляемого блока» и
«последняя асана всей секвенции». Если хвост непустой, Y в примере выше не
является последним элементом секвенции. TypeSafe видит правого соседа C
на всех шагах и учитывает переход к нему при завершении блока.
До последнего шага он также знает, что перед C будут ещё новые элементы.

Текущий запрос имеет приоритет при выборе новых поз, например при изменении
пожеланий к сложности. Он не разрешает заменить фиксированные элементы.
Имена и теги каталога передаются как данные, а не инструкции.
Модель не получает старый текстовый ответ ассистента вместо полного состава.

## 3. Каталог, кандидаты и повторы

Использовать текущие настройки каталога, папки, `language=en` и загрузки
с тегами без rigman. Новые candidates должны иметь миниатюру и непустой
catalog UUID для Save. Недоступные items не подставляются из текста модели.
Существующие items берутся из snapshot и не обновляются сетевым поиском:
даже если прежний item больше не доступен в каталоге, его снимок сохраняется.

Из кандидатов до вызова TypeSafe исключить совпадения с **любым** исходным
элементом, включая хвост, и с уже выбранными новыми items. Идентичность
проверяется по существующему правилу `same_catalog_item`: одинаковый ID
или одинаковый непустой UUID без учёта регистра.
Исходные повторы, если они уже есть в выбранном snapshot, сохраняются;
фича запрещает создавать новые повторы, а не исправляет старые.

После загрузки каталога используются существующие пакет кандидатов
`BATCH_SIZE=10` и логика предпочтения финишных поз в последней позиции.
Жёсткие фильтры применяются до выборки пакета, а не только в prompt.
Финишная выборка применяется только при выборе последнего элемента **всей**
секвенции. При непустом хвосте окончание блока не включает этот режим.

Criteria Choice строятся из реальных кандидатов с ID, именами, `bilateral`
и тегами. Ответ принимается только для существующего ID из переданного набора.
Отсутствующий ответ, неизвестный ID, пустой набор или ошибка TypeSafe означают
ошибку подбора. При последнем кандидате shortcut также не обходит фильтры.
Произвольный порог confidence в этой фиче не вводится; сохраняется текущая
политика выбора. Уверенность модели не заменяет детерминированные проверки.

## 4. Правила позиций

Сохранить общие предпочтения генерации: соответствие запросу, чередование
сгибаний и разгибаний, наличие скрутки и предпочтение завершающей позы в конце.
Они оцениваются на итоговой секвенции, включая исходные элементы.
Например, существующая скрутка уже учитывается, а исходная завершающая поза
в сохранённом хвосте не требует выбрать ещё одну на границе блока.
Если предпочтение невозможно выполнить без изменения исходных items,
фиксированные элементы сохраняются.

Для **новых** поз действуют ограничения:

- `Other/Starting` допускается только в итоговой позиции 1.
- При вставке в начало первая новая поза подбирается TypeSafe среди пригодных
  `Other/Starting`. Распределение случайного старта 10/60/30 относится к обычной
  генерации и не запускается заново для добавляемого блока.
- Если новая поза занимает итоговую позицию 2 и первая лежит, кандидат должен
  иметь `Position/Lying on the back`.
- Если новая поза занимает итоговую позицию 2 и первая стоит, исключаются
  любые `Position/Lying…`; TypeSafe предпочитает стоячую позу.
- При вставке ровно одной позы в начало второй позой будет прежний первый
  элемент. Кандидаты на новую первую фильтруются по совместимости с этим
  фиксированным вторым элементом по тем же правилам.
- При вставке двух или более поз в начало правила первого/второго элемента
  применяются к первым двум новым позам.

Проверка первой/второй пары выполняется, только когда добавление меняет состав
этой пары. Добавление после второй позиции не перепроверяет и не исправляет
пару, ранее изменённую заменой или обменом. Ограничение второй позы имеет
приоритет над предпочтением финишной, как при обычной генерации.

Исходная первая поза при вставке в начало сдвигается и сохраняется даже при
`Other/Starting`: ограничение новых стартовых поз не требует изменить или
удалить прежнее вхождение. Аналогично, добавление в конец оставляет прежнюю
завершающую позу на её месте. TypeSafe учитывает её в переходе к новым позам,
а новое окончание подбирается с предпочтением `Other/Finishing`.

Если допустимых новых стартовых поз или второй позы нет, весь блок отклоняется.
Случайный старт, игнорирование правила или замена фиксированного соседа
не используются как fallback. Предпочтение завершения, в отличие от правил
первой/второй пары, допускает обычный fallback на доступные кандидаты.

## 5. Атомарность и совместимость

Ни один выбранный item не меняет состояние секвенций до подбора всего блока.
Ошибка на шаге j, нехватка кандидатов или отказ итоговой проверки отбрасывают
все K новых элементов. Нельзя автоматически повторить всю генерацию
или сохранить успешно выбранные `j-1` items как завершённое добавление.

Обычная генерация сохраняет прежний случайный/явный старт, правила второй
позы, размер пакета, логику финиша, count и длительность 40/80 секунд.
Добавление работает по точному числу элементов K; первоначальный бюджет
длительности не ограничивает расширение секвенции. Новая длительность,
если показывается существующим UI, вычисляется из фактического нового состава.
Изменения режима вставки не добавляют новых настроек провайдера или SDK.
