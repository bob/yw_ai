# Приёмка ограниченной истории — фича 010

Связанный документ: [README](README.md).

## 1. Структура запроса

1. Короткий диалог передаётся без изменений и без summarizer call.
2. Превышение max завершённой историей приводит к одной суммаризации;
   итоговая проекция укладывается в target. При следующем model call в том же
   запросе используется та же сводка, без нового вызова суммаризатора.
3. Пары assistant/tool и несколько последовательных tools одного хода
   сохраняются целиком. Проекция не содержит orphan tool messages.
4. Большой текущий запрос, промежуточные ответы и результаты текущих tools
   не теряются даже при превышении budget текущим ходом.
5. Уже покрытые ходы не повторяются в raw history и не суммаризируются заново.
   Второе сокращение получает прежнюю сводку и только новые старые ходы.
6. Старые полные sequence tool messages проецируются в компактный формат 009
   до подсчёта budget, не изменяя исходные сохранённые сообщения.

## 2. Поведение диалога

7. Предпочтение из старого user message сохраняется в сводке; более новая
   явная отмена/замена имеет приоритет. Одноразовая просьба не становится
   постоянным правилом. Контент catalog items не становится инструкцией.
8. Неоднозначные «её», повтор имени и ссылка на исчезнувший старый контекст
   требуют уточнения, без генерации или фиктивного редактирования.
9. Выбранный старый вариант остаётся источником occurrence UUIDs и позиций,
   даже если summary упоминает более новую успешную операцию.
10. `generation_request`, все snapshots, семейная история, Save и Regenerate
    до/после сокращения совпадают. Между сессиями summary не разделяется.

## 3. Ошибки и интеграция

11. Отказ/таймаут/невалидный ответ суммаризатора сохраняет прежнюю сводку,
    ограничивает raw suffix до max, не запускает собственных повторов
    и не блокирует запрос, который разрешим по текущему состоянию.
12. Незакрытый tool call после предыдущей ошибки получает корректный result
    до проекции. Итоговая история допускается провайдером.
13. Суммаризация не вызывает каталог, generator или TypeSafe, не создаёт
    commit и не меняет лимит одной операции текущего запроса.
14. Rerun и просмотр истории не вызывают суммаризацию. Повторный model call
    в одном ходе не создаёт дополнительную summary или дубликат её coverage.
15. Невалидные значения budget отклоняются при инициализации; target и summary
    не могут быть больше max. Локальный fallback token counter явно обозначен.

## 4. Измерения

Offline scripted model фиксирует полный исходящий список сообщений и число
вызовов. Fake summarizer возвращает заранее проверяемую сводку; fixtures
покрывают разный размер сообщений и ошибки. Это проверяет структуру,
но не доказывает качество живой суммаризации.

Для семантической проверки отдельно использовать репрезентативный диалог
на GPT с fake каталогом/generator и без Jev API. Проверять сохранение/отмену
предпочтений и уточнение потерянной ссылки. В отчёте указать, выполнялся ли
этот этап и его фактический usage.

На одинаковом 50-turn fixture сравнить baseline 009 и after 010: normal calls,
summary calls, input/output/cache-read tokens, размеры последних запросов.
Выполнить существующие проверки истории вариантов, addition/swap/replacement,
progress, ошибок и AppTest. Записать результаты в README после реализации.
