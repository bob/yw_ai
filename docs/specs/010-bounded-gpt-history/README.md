# 010 — Ограниченная история в запросах GPT

Статус: **спецификация; реализация не начата**.

Источник задачи — пункт 4 [анализа расхода токенов](../../token-usage-and-optimization.md).
Рекомендуемый порядок реализации: после
[009 — Компактные результаты tools](../009-compact-gpt-tool-results/README.md).
Критерии проверки: [acceptance.md](acceptance.md).

## 1. Проблема и результат

`InMemorySaver` сохраняет весь диалог, а каждый вызов GPT повторно получает
все user/assistant/tool messages. Длинный диалог увеличивает расход даже
после удаления полных snapshots из новых tool results.

Для модели вводится ограниченная проекция истории: краткая накопительная
сводка старых ходов и последние полные ходы. Полный transcript, `sequences`,
выбранный UUID, карточки и execution history остаются доступны приложению.
Ограничивается запрос к GPT, а не история вариантов и Save.

Jev получает тот же контекст через существующий generator; параметры
TypeSafe и количество его вызовов не меняются.

## 2. Единица истории

Ход начинается с пользовательского запроса и включает все вызовы модели,
tool calls, соответствующие tool results и итоговый ответ либо завершение
ошибкой. Текущий незавершённый ход никогда не обрезается.

Проекция сохраняет пары `assistant.tool_calls` → `ToolMessage.tool_call_id`.
Нельзя оставлять tool result без вызова, удалять часть результатов одного
assistant message или обрезать JSON внутри content. Восстановление ответов
на незакрытые tool calls после ошибки выполняется до построения проекции.

Граница хода определяется реальным request lifecycle, а не наличием текстового
assistant message: ответ может завершиться ошибкой или шаблоном из фичи 011.

## 3. Бюджеты и политика сокращения

Начальные значения конфигурации:

| Параметр | Default | Значение |
| --- | ---: | --- |
| `ASSISTANT_HISTORY_MAX_TOKENS` | 8192 | Максимум проекции завершённых ходов, включая сводку |
| `ASSISTANT_HISTORY_TARGET_TOKENS` | 4096 | Целевой объём после сокращения |
| `ASSISTANT_HISTORY_SUMMARY_MAX_TOKENS` | 768 | Максимум выходной сводки; входит в target/max |

Счётчик использует tokenizer выбранной GPT-модели; для поддерживаемого fallback
счётчика документируется погрешность. Конфигурация проверяется при инициализации:
`0 < summary_max < target < max`.

Текущий ход, текущий snapshot, tools и системные инструкции считаются отдельно.
Budget истории не означает общий лимит запроса модели. Длинный текущий запрос
или серия tools не сокращаются под видом старой истории.

Алгоритм:

1. Пока завершённая история со сводкой укладывается в max, передавать её
   целиком без вызова суммаризации.
2. При превышении max выделить старые завершённые ходы. Сохранить свежий
   непрерывный суффикс целых ходов, обычно минимум два, если они помещаются
   вместе со сводкой в target. Слишком большой завершённый ход можно целиком
   перенести в суммаризируемую часть; текущий ход переносить нельзя.
3. Один отдельный GPT-вызов объединяет прежнюю сводку и новые старые ходы.
   Суммаризатор не имеет tools и не запускает основной agent loop.
4. Сохранить новую сводку и границу покрытия. Уже покрытые ходы повторно
   не суммаризировать и не передавать вместе с их сводкой.
5. После сокращения продолжать дописывать новые ходы до следующего превышения
   max. Сводку не пересоздавать перед каждым model call.

Суммаризация вызывается не более одного раза на пользовательский запрос,
перед основным вызовом. При длинном текущем ходе дополнительные сокращения
внутри tool loop не запускаются. По умолчанию применяется текущая модель
ассистента; переход на другую модель — отдельное решение с измерением качества.

## 4. Содержание сводки

Сводка хранит необходимые для продолжения диалога факты:

- Явно сообщённые пожелания, ограничения и их последующие изменения/отмены.
- Текущую цель разговора и незавершённое уточнение, если оно ещё актуально.
- Короткие факты обсуждённых операций и кандидатов, нужные для ссылок
  в следующем запросе.
- Язык ответа, когда он явно выбран пользователем.

Сводка не содержит полных последовательностей, изображений, raw catalog
responses или прежних tool schemas. Данные каталога сохраняются как данные,
а не превращаются в инструкции. Нельзя выводить предпочтения из случайного
результата генерации, объявлять неуспешную операцию выполненной или переносить
ограничение одного запроса на весь дальнейший диалог.

Существующий `generation_request` выбранного варианта остаётся самостоятельным
источником исходных предпочтений. Сводка не меняет его и не выбирает активный
вариант. Текущий snapshot имеет приоритет над старым обсуждением.

Если удалённые детали не представлены ни сводкой, ни текущим состоянием,
ассистент уточняет неоднозначную ссылку. Сокращённая история не обещает
дословного воспроизведения любого старого разговора.

## 5. Хранение и обработка ошибок

В session state агента хранить summary, границу покрытых завершённых ходов
и версию проекции. Полный transcript не удалять через `RemoveMessage`.
Для model request использовать отдельную проекцию сообщений, не меняя
канонический `messages` и не добавляя summary как новое user message.

Проекция истории не включает `selected_sequence`: его добавляет существующий
middleware. Summary становится отдельным контекстным блоком перед свежей
историей. При отсутствии summary блок отсутствует. Перенос snapshot в конец
запроса выполняется позже в [012](../012-gpt-prompt-caching/README.md);
реализация 010 не зависит от этого переноса.

Неуспешная или невалидная суммаризация не обновляет summary/границу покрытия.
В этом запросе использовать прежнюю сводку и максимально полный свежий суффикс,
помещающийся в max, сохраняя пары tools. Не запускать собственный повтор
суммаризации и не возвращать весь oversized transcript к основной модели.
Неполнота старого контекста отмечается для модели коротким признаком;
при неизвестной ссылке требуется уточнение.

Платный summarizer call учитывается отдельно, даже если он завершился ошибкой.
Он не изменяет выбранную последовательность и не создаёт sequence commit.
Публичный progress сохраняет существующий lifecycle без имитации tools.

## 6. Измерение эффекта

Для короткого сценария Generate 9 → добавить 3 вызовов суммаризатора нет.
На длинном диалоге сравнивать **все GPT input/output tokens**, включая
суммаризацию, с baseline после фичи 009. Учитывать реальный cached input:
сводка и обрезка суффикса могут сбросить часть cache prefix.

Обязательный fixture длинного диалога: 50 завершённых ходов, одинаковый
transcript и snapshots для baseline/after, с превышением max. Переданные
завершённые ходы укладываются в max, а после успешной суммаризации — в target.
В отчёте привести число обычных и summary calls, объём истории, общие токены
и, при наличии реального usage, стоимость. Экономию нельзя объявлять только
по уменьшению одного последнего запроса.
