# Фича 002: Прогресс выполнения запроса ассистента

Статус: **реализовано; пункты 1–6 выполнены**. Создано: 2026-10-09.
Проверки: [приёмочные сценарии](acceptance.md).

Связанные документы: [общий агент](../001-create-assistant-agent/assistant-agent.md),
[контекст и варианты секвенции](../001-create-assistant-agent/sequence-context.md).
Эта фича уточняет отображение stream-событий общего агента.

## 1. Проблема и цель

После отправки запроса пользователь видит своё сообщение, но до первого
результата интерфейс не объясняет, что происходит. Особенно заметно ожидание
ответа модели, поиска в каталоге и начала генерации секвенции.

Нужно сразу показывать `Thinking...`, затем менять текущий статус по мере
выполнения: например, `Searching catalog items...` и `Generating sequence...`.
Этапы и доступные промежуточные сообщения собираются в одном раскрываемом
блоке. После завершения блок автоматически сворачивается, а итоговый ответ
и секвенция остаются в привычном виде.

## 2. Текущее устройство

- [AssistantAgent.stream_response_events](../../../src/langchain_app/services/assistant_agent.py)
  использует `stream_events(version="v3")` с проекциями `custom` и `values`.
  Middleware публикует начало/окончание модели и tools; observer — поиск
  внутри генератора. Типизированный поток подтверждает commit после сохранения
  состояния (`durability="sync"`). Адаптеры `stream` и `generate` сохраняют
  прежнюю выдачу элементов и финального текста. UI чата, Generate и Regenerate
  потребляет типизированный поток через общий рендерер прогресса.
- [Tools](../../../src/langchain_app/tools/sequence.py) передают выбранные
  элементы генерации через `runtime.stream_writer`. Middleware превращает их
  в предварительные `sequence_element` и счётчики этапа. Возврат `Command`
  ещё не означает commit; полное состояние подтверждает `sequence_committed`.
- [SequenceRenderer](../../../src/langchain_app/ui/sequence.py) выводит текст
  и миниатюры вне status; `sequence_committed` переключает область секвенции
  на полный сохранённый вариант. Неподтверждённые миниатюры убираются.
- [Entrypoint](../../../src/langchain_app/assistant.py) принимает запросы через
  callbacks, блокирует повторные действия и сохраняет каждый ответ в
  `st.session_state.messages`, включая пустые ответы и ошибки. Снимки Regenerate
  добавляются к истории конкретной карточки; rerun воспроизводит их без запроса.

## 3. Поведение интерфейса

### Начало и выполнение

1. Сразу после принятия запроса появляется сообщение ассистента со свёрнутым
   блоком выполнения и статусом `Thinking...`. Блок создаётся до инициализации
   зависимостей и первого обращения к модели или каталогу.
2. Заголовок блока показывает одно сообщение с индикатором выполнения.
   Названия этапов, краткие результаты и публичные промежуточные сообщения
   ассистента сменяют друг друга в этой строке. Под строкой прогресса
   сообщения не отображаются.
3. Названия этапов и сообщения о результатах остаются в строке минимум
   0,6 секунды перед заменой, чтобы быстрые события можно было заметить.
   Последовательные обновления счётчика поз не требуют такой паузы.
   Пользователь может вручную свернуть или раскрыть блок во время работы;
   обновление статуса не должно принудительно раскрывать его снова.
4. Миниатюры продолжают появляться по мере генерации в области секвенции
   вне блока выполнения. Статус может уточняться до
   `Generating sequence... 3/12 poses`, если общее число уже известно.
5. Повторные обращения к модели и tools создают новые записи: например,
   поиск → обдумывание результата → повторный поиск. Порядок этапов определяется
   выполнением, а не заранее заданным сценарием.

### Завершение

После успешного завершения всего запроса, включая итоговый ответ модели:

- Индикатор выполнения исчезает; заголовок становится `Completed in N s`.
- Блок автоматически сворачивается, сохраняя возможность раскрыть детали.
- Полный журнал этапов и результатов доступен при раскрытии завершённого блока.
- Итоговый текст, карточка секвенции, Save и навигация вариантов отображаются
  вне блока, как сейчас. Промежуточные сообщения не добавляются к итоговому тексту.
- Rerun воспроизводит завершённый блок свёрнутым, без повторного запуска запроса.

Это поведение применяется к обычному чату, Generate, Regenerate, поиску,
получению тегов и замене элемента. Ответ без tools тоже получает цикл
`Thinking...` → итоговый ответ → свёрнутый блок.

### Пример

Во время работы заголовок последовательно меняется:

```text
Thinking...
Searching catalog items...
Generating sequence... 3/12 poses
Preparing response...
```

После завершения пользователь видит:

```text
▸ Completed in 18 s

Итоговый ответ ассистента
[Карточка секвенции и существующие кнопки]
```

При раскрытии доступны выполненные этапы и их краткие результаты. Числа
в примере иллюстративные; длительность и прогресс берутся из текущего запроса.

## 4. Источники статусов

| Реальное действие | Заголовок текущего этапа | Краткий результат в деталях |
| --- | --- | --- |
| Первое обращение к модели или выбор следующего действия | `Thinking...` | Завершённый этап обращения к модели |
| `get_catalog_tag_names` | `Loading catalog tags...` | Количество полученных тегов |
| `search_catalog_items` | `Searching catalog items...` | Количество возвращённых элементов, включая ноль |
| Загрузка кандидатов из каталога внутри `SequenceGenerator` | `Searching catalog items...` | Количество пригодных кандидатов |
| `generate_sequence`, подбор и выдача элементов | `Generating sequence...` | Количество выданных элементов; после commit — секвенция создана |
| `replace_sequence_element` | `Updating sequence...` | Элемент заменён либо изменение не требовалось |
| Обращение к модели после tool | `Thinking...` | Следующее действие либо подготовка ответа |
| Получение итогового публичного текста | `Preparing response...` | Ответ подготовлен |

Статусы переключаются при начале реальной работы. Не менять их по таймеру,
не добавлять искусственные задержки и не показывать поиск, если его не было.
Во время tool заголовок отражает tool или его текущий подэтап, а не ожидание
модели. При возвращении к модели снова показывается `Thinking...`.

Внутренний поиск генератора — подэтап генерации; он не означает, что агент
вызвал отдельный `search_catalog_items`. После получения кандидатов заголовок
возвращается к `Generating sequence...` до выбора и выдачи элементов.

Подтверждение создания или замены секвенции появляется только после записи
полного снимка в состояние агента. Последняя миниатюра сама по себе не означает
успешный commit. Процент общей готовности запроса не вычисляется; `3/12`
относится только к элементам секвенции.

## 5. Промежуточные сообщения модели

Показывать публичный текст ассистента, сопровождающий промежуточное действие,
если модель его возвращает: например, «Поищу подходящие элементы в каталоге».
Текст из `AIMessage` с tool calls относится к деталям выполнения. Финальное
сообщение без tool calls или уточняющий вопрос относится к итоговому ответу.

Отсутствие промежуточного текста допустимо: для обратной связи достаточно
статусов и кратких фактических результатов tools. Не требовать отдельного
LLM-вызова для описания каждого этапа.

Отображать только публичные текстовые блоки. Внутренние reasoning-блоки,
system prompt, сырые аргументы tools, JSON-ответы и технические трассировки
не входят в пользовательский журнал. Название `Thinking...` обозначает
ожидание модели и не требует доступа к её внутренним рассуждениям.

Первый этап может получать публичные сообщения целиком через `updates`.
Посимвольный или токенный вывод текста — отдельное улучшение; он не нужен
для немедленного индикатора и смены этапов. При его добавлении фрагменты
объединяются по идентификатору сообщения, а законченный `AIMessage`
не добавляет тот же текст второй раз.

## 6. Контракт событий и хранение

Предлагается отдельный типизированный поток `stream_response_events` для UI.
Существующие `stream` и `generate` могут оставаться адаптерами совместимости,
отбирающими из него прежние строки и элементы. UI всех перечисленных сценариев,
включая Regenerate, должен потреблять события, чтобы не потерять прогресс.

Общие поля: `request_id`, монотонный `event_index`, `type`, время от начала
запроса. Для этапов дополнительно `step_id` и, при наличии, `tool_call_id`.
Повторный вызов того же tool получает новый `step_id`.

| Событие | Назначение |
| --- | --- |
| `request_started` | Начало жизненного цикла запроса |
| `step_started` | Начало обращения к модели, tool или подэтапа; код этапа и публичный заголовок |
| `step_progress` | Краткий результат или счётчик текущего этапа |
| `step_finished` | Исход `ok`, `no_change` или `error`, длительность и краткое описание |
| `assistant_message` | Публичный текст и назначение `intermediate` или `final` |
| `sequence_element` | Предварительный элемент для существующей потоковой отрисовки |
| `sequence_committed` | UUID полного варианта после его сохранения в состоянии |
| `request_finished` | Терминальный исход `complete` или `error` и общая длительность |

`request_id` принадлежит одному запуску, а не всему thread диалога. Каждый
Generate/Regenerate получает новый ID. UI отображает события только своего
запроса и не применяет их к другой карточке. Каждый начатый этап завершается
один раз; фатальная ошибка закрывает активные этапы и весь запрос.

Агент нормализует события LangChain, tools и генератора. Начало tool
публикуется до выполнения его блокирующей работы; `updates` после возврата
tool недостаточно для своевременного индикатора. Для поиска внутри генератора
нужен необязательный callback/observer прогресса без зависимости от Streamlit
и без изменения алгоритма выбора. Tools и сервисы не вызывают `st.*`.

В `ChatMessage` добавить необязательный снимок выполнения: `request_id`,
исход, длительность, этапы и промежуточные публичные сообщения. Его хранить
в `st.session_state` рядом с итоговым ответом; он не добавляется в prompt
и не заменяет состояние секвенций. Для Regenerate снимок связывается с
конкретной попыткой и полученным вариантом; предыдущие попытки сохраняются.
Неуспешная попытка остаётся доступной, даже если новый вариант не создан.
Старые сообщения без снимка продолжают отображаться как сейчас.

Хранение ограничено текущей Streamlit-сессией, как существующая история.
Постоянное хранилище, восстановление после перезапуска и отмена запроса
не входят в эту фичу. Во время выполнения повторная отправка и кнопки,
запускающие запрос или меняющие активный вариант, недоступны; после завершения,
включая ошибку, они снова доступны.

## 7. Ошибки и частичные результаты

- При фатальной ошибке заголовок становится `Could not complete request`,
  индикатор прекращается, блок остаётся раскрытым. Понятное сообщение об ошибке
  также видно вне блока. Ошибка и детали сохраняются даже без итогового текста
  и секвенции; следующий rerun не теряет их и не запускает запрос заново.
- Если tool вернул ожидаемую ошибку и модель продолжает работу, этот этап
  отмечается как неуспешный. Весь запрос остаётся активным; после нормального
  ответа он может завершиться `complete`, сохранив ошибку этапа в деталях.
- Пустая выборка и `no_change` — нормальные результаты, а не фатальные ошибки.
- При прерванной генерации предварительные миниатюры убираются. Незавершённая
  секвенция не становится вариантом, Save для неё недоступен; прежний вариант
  сохраняется.
- Если commit уже выполнен, а финальный ответ модели не удался, новый вариант
  остаётся видимым и доступным для Save. Блок показывает ошибку подготовки
  ответа и отдельно подтверждает выполненное изменение.
- Ошибка инициализации зависимостей тоже завершает уже показанный блок ошибки.
  Время измеряется монотонными часами от принятия запроса до завершения потока,
  включая инициализацию и подготовку ответа.

## 8. Подход к реализации

Использовать нативный `st.status` внутри сообщения ассистента, с обновлением
заголовка и явным `state`. На успехе вызвать
`update(state="complete", expanded=False)`; на фатальной ошибке —
`update(state="error", expanded=True)`. Итоговый ответ и область секвенции
разместить в соседних контейнерах вне status. Для истории можно использовать
статический свёрнутый `st.expander` или завершённый `st.status`.
Эти операции поддерживаются [Streamlit st.status](https://docs.streamlit.io/develop/api-reference/status/st.status).

LangChain поддерживает события выполнения агента и пользовательские
обновления. Текущий `stream_events(version="v3")` можно расширить нужными
проекциями и нормализовать в контракт приложения.
См. [LangChain streaming](https://docs.langchain.com/oss/python/langchain/streaming).
Конкретные transformers и сигнатуры проверить по установленной версии
при реализации; UI не должен зависеть от сырого формата библиотеки.

## 9. Критерии приёмки

Проверки с fake model, управляемыми fake services и Streamlit AppTest;
немедленную отрисовку до завершения медленного вызова дополнительно проверить
в браузере на искусственно задержанном сервисе.

- До возврата первого результата модели или сервиса виден `Thinking...`.
- Пока поиск ещё выполняется, уже виден `Searching catalog items...`.
- Генерация показывает загрузку каталога, затем подбор секвенции; миниатюры
  появляются до завершения генератора, а счётчик соответствует выданным элементам.
- Цепочка tags → search → replace показывает реальные этапы в их порядке.
  Повторный поиск добавляет новую запись; tool, который не вызывался, не появляется.
- Публичное промежуточное сообщение видно внутри блока и отсутствует
  в итоговом `content`. Итоговый ответ отображается один раз вне блока.
- После успешного ответа блок свёрнут; его можно раскрыть. Длительность,
  промежуточные сообщения и завершённые этапы доступны после rerun.
- Запрос без tools, Generate и Regenerate используют тот же жизненный цикл.
  Ошибка Regenerate сохраняется отдельно от прежней успешной попытки.
- Пустой поиск и `no_change` завершаются корректно. Фатальная ошибка останавливает
  индикатор, сохраняет диагностику и снова разрешает отправку запроса.
- Ошибка до commit не создаёт частичный вариант; ошибка после commit
  сохраняет созданный вариант, историю и Save.
- События двух запросов и двух Streamlit-сессий не смешиваются; обычный rerun
  и раскрытие истории не вызывают модель, tools или генератор повторно.
- Существующие Save, выбор активного варианта и Previous/Next сохраняют поведение;
  старые сообщения без истории выполнения отображаются без ошибки.
