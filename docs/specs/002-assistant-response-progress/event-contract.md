# Фича 002: Контракт событий и снимка выполнения

Схемы реализованы в
[schemas/response_progress.py](../../../src/langchain_app/schemas/response_progress.py)
и экспортируются из `langchain_app.schemas`. Они используют Pydantic и не зависят
от LangChain или Streamlit. Неизвестные поля запрещены, как в остальных
`ApiSchema` проекта.

## Общие поля событий

- `request_id: UUID` — ID одного запуска. Его назначает вызывающий код либо
  производитель потока, если ID не передан; схема не создаёт отдельный ID
  для каждого события.
- `event_index: int` — неотрицательный индекс события, начиная с нуля.
- `elapsed_seconds: float` — конечное неотрицательное время от принятия
  запроса, измеренное монотонными часами, в секундах.
- `type` — фиксированный строковый тип события.

Объединение `ResponseEvent` выбирает конкретную схему по полю `type`.
Для проверки или восстановления сериализованных событий используется
`TypeAdapter(ResponseEvent)` либо `TypeAdapter(list[ResponseEvent])`.

Отслеживание возрастания индексов и времени, публикация начала запроса до
инициализации зависимостей и однократное завершение каждого этапа относятся
к производителю потока: отдельная схема проверяет только одно событие.

## Payload событий

Все события этапов, включая выдачу элемента и commit, содержат `step_id: UUID`
и необязательный `tool_call_id: str`. Для повторного вызова создаётся новый
`step_id`; `tool_call_id` сохраняет идентификатор вызова библиотеки.

| Тип / схема | Дополнительные поля |
| --- | --- |
| `request_started` / `RequestStartedEvent` | Необязательный `source_sequence_uuid` — исходный вариант для Regenerate или редактирования |
| `step_started` / `StepStartedEvent` | `code`, публичный `title`, необязательный `parent_step_id` для подэтапа |
| `step_progress` / `StepProgressEvent` | Необязательные `summary`, `completed`, `total`; хотя бы одно поле должно быть задано |
| `step_finished` / `StepFinishedEvent` | `outcome: ok \| no_change \| error`, `duration_seconds`, публичный `summary` |
| `assistant_message` / `AssistantMessageEvent` | Публичный `text`, `purpose: intermediate \| final`, необязательные `message_id` и `step_id` |
| `sequence_element` / `SequenceElementEvent` | `order` от 1, полный `catalog_item: CatalogItemSchema`; предварительный элемент |
| `sequence_committed` / `SequenceCommittedEvent` | `sequence_uuid: UUID` полного варианта, уже сохранённого в состоянии агента |
| `request_finished` / `RequestFinishedEvent` | `outcome: complete \| error`, `duration_seconds`, `error_message` для фатальной ошибки |

Коды `StepCode`: `thinking`, `loading_catalog_tags`, `searching_catalog_items`,
`generating_sequence`, `updating_sequence`, `preparing_response`.
Код обозначает действие, а `title` содержит его публичный заголовок.
Внутренний поиск генератора получает `parent_step_id` этапа генерации.

Удаление [015](../015-remove-sequence-elements/README.md) использует
`updating_sequence` с заголовком `Removing sequence elements...`.
Успешный summary берёт K и итоговый размер из `removal.removed_count`
и `elements_count`, например `Removed 2 sequence elements; 3 poses in total.`
Один `sequence_committed` публикуется после доступности полного snapshot
в state и перед `step_finished`. Удаление не создаёт предварительные
`sequence_element`, счётчики `step_progress`, поиск или галерею каталога.
Ожидаемая ошибка завершает этап с `error`, без commit и новой карточки.

Счётчики — целые неотрицательные числа. `completed` может поступить без
известного `total`, а `total` — до первого элемента. Если заданы оба,
`completed <= total`. Нулевой результат поиска допустим. Счётчик относится
к текущему этапу, а не к общей готовности запроса.

Публичный текст не может быть пустым или состоять только из пробелов.
Производитель извлекает публичные текстовые блоки и не передаёт reasoning,
аргументы tools или технические трассировки. `message_id` позволяет связывать
текст с исходным сообщением; токенные фрагменты в текущий контракт не входят.

Ошибка отдельного этапа допустима при итоговом `complete`. `error_message`
обозначает только фатальную ошибку всего запроса: для `error` он обязателен,
для `complete` отсутствует. Сообщение должно быть пригодно для показа в UI.

## Снимок выполнения

`ExecutionSnapshot` хранит завершённую попытку:

- `request_id`, `outcome`, `duration_seconds`, необязательный `error_message`;
- `steps: list[ExecutionStepSnapshot]` — этапы в порядке начала, включая
  повторные вызовы и подэтапы;
- `intermediate_messages: list[ExecutionMessageSnapshot]` — промежуточный
  публичный текст с индексом, временем и необязательными `step_id` / `message_id`;
- необязательный `source_sequence_uuid` — исходный вариант;
- необязательный `sequence_uuid` — вариант, созданный или изменённый этой
  попыткой и уже сохранённый в состоянии.

`ExecutionStepSnapshot` содержит идентификаторы и описание этапа, индекс
и время его начала (`event_index`, `elapsed_seconds`), исход, длительность,
итоговый `summary` и все публичные обновления `progress`.
`ExecutionStepProgress` сохраняет индекс, время, краткий результат и счётчики
отдельного обновления. Индексы сообщений и обновлений позволяют сохранить
их порядок относительно начала этапов.

Схема запрещает повторные `step_id` в одной попытке, ссылки на отсутствующий
родительский этап, ссылку этапа на самого себя и привязку промежуточного
сообщения к отсутствующему этапу. Списки по умолчанию независимы у разных
экземпляров снимка.

Ошибка до commit оставляет `sequence_uuid=None`. Если финальный ответ не
удался после commit, снимок содержит `outcome="error"` и UUID сохранённого
варианта. Ошибка инициализации может иметь пустые `steps` и
`intermediate_messages`. Итоговый текст хранится в `ChatMessage.content`.

В [ChatMessage](../../../src/langchain_app/schemas/chat.py) добавлены
необязательные поля:

- `execution: ExecutionSnapshot | None` — последняя завершённая попытка;
- `execution_history: list[ExecutionSnapshot]` — предыдущие попытки в порядке
  выполнения. Перед заменой `execution` его снимок переносится в историю.

Такой контракт позволяет сохранить неудачный Regenerate рядом с предыдущими
попытками даже без нового варианта. Сообщения без этих полей остаются валидными.
Снимки предназначены для истории сессии и не передаются в prompt.

Для JSON используется `snapshot.model_dump(mode="json")`, для восстановления —
`ExecutionSnapshot.model_validate(payload)`. UUID сериализуются строками,
вложенные снимки и публичные обновления восстанавливаются с валидацией.

## Производитель потока (пункты 2–3)

[AssistantAgent.stream_response_events](../../../src/langchain_app/services/assistant_agent.py)
возвращает `Iterator[ResponseEvent]` и принимает `request`, `require_generation`,
`regenerate_sequence_uuid` и необязательный `request_id`. Каждый запуск без
переданного ID получает новый UUID. Regenerate использует исходный запрос
сохранённого варианта, как прежде.

Первый `next()` выдаёт `request_started` до создания графа/модели и вызова
factory генератора. `custom` несёт внутренние сигналы, `values` — объединённое
состояние графа. Нормализатор присваивает общий порядок и монотонное время;
внешний потребитель видит только схемы приложения. Реальные начала и окончания
публикуют [middleware](../../../src/langchain_app/services/response_progress_middleware.py).
Повторные model calls и tools получают отдельные этапы. Публичный текст
извлекается из `AIMessage.text`: сообщение с tool calls имеет назначение
`intermediate`, без них — `final`. Reasoning и сырые payload не публикуются.

[SequenceGenerator.generate](../../../src/langchain_app/services/sequence_generator.py)
принимает необязательный `progress_observer`. Observer получает
`GeneratorSearchProgress` с фазами `started`/`finished`, исходом поиска и числом
кандидатов с изображениями после загрузки/валидации. Это подэтап генерации,
связанный с родителем и его `tool_call_id`, а не отдельный вызов search tool.
Успешное окончание поиска публикует обновление родительского этапа до выбора
первой асаны. Алгоритм подбора и работа без observer сохраняются.

Элементы выдаются немедленно как `sequence_element` с порядковым номером;
за ними идут `step_progress` со счётчиком. Возврат `Command` регистрирует только
ожидающий commit. `sequence_committed` и успешное окончание операции выдаются
после подтверждения полного варианта в состоянии. `durability="sync"` позволяет
сразу получить вариант через `get_sequence()` при получении события commit.
Последний элемент, `no_change` и неуспешная операция не подтверждают новый вариант.

Восстановимая ошибка tool завершает только этот этап; запрос может закончиться
`complete`. Фатальная ошибка завершает все оставшиеся этапы и выдаёт
`request_finished(outcome="error")` с публичным сообщением, после чего
исходное исключение распространяется вызывающему коду. Ошибки OpenAI и лимита
графа по-прежнему оборачиваются в `AssistantAgentError`. Получатель должен
сохранить терминальное событие и обработать исключение, не создавая вторую
запись ошибки. Созданный вариант сохраняется при ошибке следующего model call;
при ошибке до commit частичный вариант не создаётся.

`stream` отбирает только элементы и финальные сообщения, `generate` — только
элементы. Промежуточный текст не попадает в прежний итоговый ответ.
UI чата, Generate и Regenerate подключён к событиям; адаптеры не используются
основной Streamlit-страницей.

## Потребитель и история (пункты 4–5)

[PendingResponse и ResponseProgressRenderer](../../../src/langchain_app/ui/response_progress.py)
создают ID и отмечают монотонное время принятия запроса в callback. Очередь
`st.session_state.pending_response` позволяет следующему проходу страницы
показать отключённые Generate, chat input, Regenerate и навигацию до работы
агента. `Thinking...` создаётся до вызова фабрики зависимостей. По окончании
очередь очищается в `finally`, ответ сохраняется и страница делает rerun.

Время событий сдвигается на инициализацию зависимостей; общая длительность
включает время от принятия запроса, а длительность каждого этапа остаётся
временем его фактической работы. Обновления работающего status не передают
`expanded`, сохраняя ручное сворачивание. Успех сворачивает блок, фатальная
ошибка раскрывает его и показывает публичное сообщение рядом с результатом.

[ResponseExecution](../../../src/langchain_app/services/response_execution.py)
собирает типизированный снимок без зависимости от Streamlit. События другого
`request_id`, повторные индексы и повторный публичный текст с тем же
`message_id` игнорируются. Итоговый текст хранится отдельно от промежуточного.
Ошибка инициализации или оборванный поток без терминального события закрывают
активные этапы и создают один `request_finished(error)`; уже полученная ошибка
производителя повторно не добавляется. Технический текст исключения не попадает
в пользовательскую историю.

Карточка результата появляется только по `sequence_committed`; предварительные
изображения после ошибки без commit очищаются. После commit вариант остаётся
доступным при ошибке финального ответа. Regenerate переносит прежний `execution`
в `execution_history` даже при неудаче без нового варианта. Каждый снимок хранит
UUID источника и, при commit, UUID результата. Старые сообщения без снимков
продолжают отображаться.

## Проверка

[tests/test_response_progress_schemas.py](../../../tests/test_response_progress_schemas.py)
проверяет сериализацию всех восьми типов событий и снимка, границы времени
и счётчиков, запрет сырых полей, публичные сообщения, ссылки этапов, `no_change`,
восстановимую ошибку tool, ошибки до и после commit и необязательные поля чата.

```bash
uv run python -m unittest discover -s tests -p test_response_progress_schemas.py -v
```

[tests/test_response_progress_stream.py](../../../tests/test_response_progress_stream.py)
проверяет реальный цикл агента с fake model: события до завершения блокирующих
вызовов, поиск генератора, поток элементов, доступность снимка при commit,
повторные вызовы, публичный текст, `no_change`, восстановимые и фатальные ошибки,
Regenerate и сохранение варианта после ошибки финального ответа.
Отдельные проверки observer добавлены в
[tests/test_sequence_generator.py](../../../tests/test_sequence_generator.py).

[tests/test_response_progress_ui.py](../../../tests/test_response_progress_ui.py)
проверяет завершённые и неудачные попытки через Streamlit AppTest, повторный
поиск, промежуточные сообщения, длительность и ошибки инициализации, счётчики,
ошибки до/после commit, повторный Regenerate, блокировку действий, старые
сообщения, разные сессии и фильтрацию чужих событий. Существующие проверки
вариантов также проверяют сохранение ошибки и исход `no_change`.

Результаты полного набора и проверки задержанных вызовов в браузере —
в [приёмочных сценариях](acceptance.md).
