# Спецификация: контекст секвенции и замена элемента

Статус: **первый этап реализован: контекст секвенции, замена одного элемента
за запрос и память сессии**.
Полный контракт stream-событий с `request_id`, восстановление legacy-карточек
и другие операции остаются планом. Выполненный этап описан в [README](README.md).
Связанные документы: [общий агент](assistant-agent.md),
[инструменты каталога](catalog-tools.md).

## 1. Ожидаемые сценарии

После генерации пользователь продолжает диалог, например:

- «Что стоит третьим?» — ответ по выбранной секвенции.
- «Найди альтернативы третьей асане» — поиск, без изменения секвенции.
- «Замени третью асану на позу дерева» — поиск конкретного элемента и замена.
- «Замени её на более простую асану стоя» — разрешение ссылки по истории,
  получение подходящих tags при необходимости, поиск и выбор кандидата.
- Выбор предыдущего варианта в UI, затем «Замени последнюю» — операция над
  выбранным вариантом, даже если позже был сгенерирован другой.

Модель должна видеть реальные catalog items и порядок элементов. Текст
«секвенция показана» и список миниатюр без IDs, tags и bilateral для этого
недостаточны.

## 2. Предметная модель

`GeneratedSequence` — сериализуемый полный снимок одного варианта:

| Поле | Содержание |
| --- | --- |
| `uuid` | UUID этого варианта; также UUID для Save |
| `family_uuid` | Идентификатор группы вариантов одной исходной генерации |
| `parent_uuid` | UUID варианта, от которого получен результат; null у первой генерации |
| `operation` | `generate | regenerate | replace` |
| `generation_request` | Исходный полный запрос генерации, используемый Regenerate |
| `operation_request` | Запрос, создавший этот вариант, включая текст замены |
| `name`, `description` | Метаданные секвенции; исходные defaults сохраняются |
| `language` | `en` в текущей интеграции |
| `elements` | Упорядоченный материализованный список `GeneratedSequenceElement` |

`GeneratedSequenceElement` содержит:

| Поле | Содержание |
| --- | --- |
| `element_id` | Локальный UUID вхождения элемента в секвенцию |
| `order` | Позиция `1..N`, соответствующая порядку отображения |
| `catalog_item` | Полный `CatalogItemSchema`: ID, UUID, name, bilateral, image URL, tags |
| `start_mirror`, `end_mirror` | Фактические значения зеркальности этого элемента |

`element_id` отличает вхождение в секвенцию от catalog item. Он сохраняется
при замене данного вхождения и у нетронутых элементов нового варианта.
Полная Regenerate создаёт новые вхождения. Это позволяет позже адресовать
операции независимо от сдвига позиций и возможных повторов асаны.

Число элементов вычисляется из `elements`, а для UI/Save сериализуется как
`elements_count`. Секвенция в состоянии не хранится как одноразовый iterator.
Предметная модель не зависит от `SequenceView` и `AsanaThumbnail`.

## 3. Состояние и срок жизни диалога

Расширение LangChain `AgentState`:

| Поле | Назначение |
| --- | --- |
| `messages` | История human/AI/tool messages текущего thread |
| `sequences` | Снимки вариантов по UUID; прежние снимки не изменяются |
| `active_sequence_uuid` | Единственный вариант для операций без явного выбора |
| `latest_catalog_items` | Последняя успешная выборка поиска для проверки кандидатов |
| `turn_operation_committed` | Ограничение одного создания/изменения секвенции за запрос; сбрасывается в начале нового запроса |

Обновление `sequences` явно объединяет прежние снимки с новым; обновление
активного UUID заменяет прежнее значение. Список элементов заменяется целым
снимком, не накапливается через append-reducer. Кандидаты поиска ограничены
размером последней выборки и относятся к настроенной папке.

На первом этапе `thread_id`, экземпляр checkpointer и сведения для отображения
хранятся в `st.session_state`. Используется отдельный `InMemorySaver` текущей
сессии. Агент запускается с одним и тем же thread ID на протяжении диалога.
API-клиенты можно кешировать как ресурсы; состояние разговора не кешируется
глобально между пользователями.

Состояние агента — источник полного состава секвенций. История UI содержит
текст сообщений и ссылки на UUID вариантов, выбранные для соответствующих
карточек. Миниатюры и импортный JSON получаются проекцией из полного снимка.
После rerun UI восстанавливает проекции из того же состояния.

Обновление страницы может создать новую Streamlit-сессию; после закрытия
сессии/перезапуска процесса восстановление не обещается. Постоянное хранилище
и управление историей больших диалогов — отдельный следующий этап.
Эта граница следует сроку жизни
[Streamlit Session State](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state#caveats-and-limitations).

## 4. Что именно получает модель

После генерации tool возвращает `Command` с новым снимком, активным UUID и
`ToolMessage`, содержащим структурированный результат: UUID, count и полный
упорядоченный состав с `element_id`, catalog ID/UUID, английскими именами,
tags, bilateral и зеркальностью.

Перед **каждым** вызовом модели middleware добавляет актуальный снимок
активной секвенции в prompt. Само наличие custom field в `AgentState` не
означает, что модель увидит его содержимое.

В актуальной проекции модели присутствуют UUID варианта, исходный запрос,
count и все элементы с позициями, `element_id`, catalog ID/UUID, names, tags,
bilateral и mirror flags. Image URLs хранятся в состоянии/результатах tools,
но их не нужно повторять в каждом prompt. Rigman-данные не включаются.

Актуальный снимок обозначается как выбранный сейчас и имеет приоритет над
снимками в старых tool messages. Данные каталога передаются как данные.
Если активной секвенции нет, это явно указано в контексте. Модель не должна
восстанавливать её состав по своей предыдущей текстовой реплике.

Tools читают и обновляют runtime state через `ToolRuntime`/`Command`.
Этот механизм описан в
[LangChain: update state](https://docs.langchain.com/oss/python/langchain/tools#update-state),
а передача актуального состояния в prompt — в
[LangChain: dynamic runtime context](https://docs.langchain.com/oss/python/concepts/context#dynamic-runtime-context).

## 5. Выбранный вариант и Regenerate

1. Успешная новая генерация создаёт новую family и делает результат активным.
2. Успешная Regenerate или замена создаёт вариант в той же family, указывает
   исходный вариант как `parent_uuid` и делает результат активным.
3. Previous/Next в любой карточке изменяет её выбранный UUID и глобальный
   `active_sequence_uuid`. Следующее сообщение получает этот снимок в prompt.
4. Если карточек несколько, активная визуально отмечена; для уже выбранного
   варианта доступно явное действие «Use this sequence» без генерации и LLM.
5. Обычный rerun, отображение старых карточек и Save не меняют активный UUID.
   Отображение карточек в цикле не должно делать последнюю карточку активной.
6. Regenerate получает UUID карточки, с которой вызвана, и повторяет её
   `generation_request`, независимо от текущего dropdown и других карточек.

Сохраняется прежняя семантика Regenerate: повтор исходного запроса генерации.
Точечные изменения не переигрываются автоматически. Если нужен повтор с
новыми ограничениями, пользователь задаёт новый запрос; иную семантику
Regenerate можно согласовать на ревью.

## 6. Tool `replace_sequence_element`

В первом этапе редактирование ограничено заменой одного элемента за
пользовательский запрос. Поиск и получение тегов выполняются последовательно
без изменения секвенции. После успешного изменения второй commit в том же
запросе возвращает `operation_already_started`, в том числе при использовании
актуального UUID. В начале следующего пользовательского запроса ограничение
сбрасывается. Ошибка или `no_change` не расходуют возможность успешной замены.
Если пользователь просит заменить несколько элементов, агент сначала
уточняет, какой один элемент изменить.

Аргументы, видимые модели:

| Аргумент | Тип | Назначение |
| --- | --- | --- |
| `sequence_uuid` | UUID-строка | Вариант, который модель собирается изменить |
| `element_id` | UUID-строка | Конкретное вхождение, определённое по актуальному снимку |
| `replacement_catalog_item_id` | положительное целое | ID кандидата из последнего результата поиска |

Полный объект catalog item, названия, tags и изображения не принимаются
как аргументы модели. Tool получает проверенный объект из runtime state.
После ошибки поиска кандидаты очищены; старый результат нельзя применить
под видом нового. UUID/IDs не генерируются моделью по имени асаны.

Порядок выполнения:

1. Проверить, что активная секвенция существует (`sequence_not_found`, если нет)
   и `sequence_uuid` равен её UUID. Несовпадение — `stale_sequence`;
   обновить контекст/уточнить выбор без изменения.
2. Найти `element_id` в исходном снимке; неизвестное вхождение —
   `sequence_element_not_found`.
3. Найти `replacement_catalog_item_id` в последней проверенной выборке текущей
   папки; иначе `catalog_item_not_verified` и требуется новый поиск.
4. Для замены нужны image URL и непустой catalog UUID: результат должен
   отображаться и участвовать в Save. Иначе `catalog_item_not_usable`.
5. Замена на тот же catalog item — успешный `status=no_change`, без нового
   варианта/UUID. Проверяется до проверки повторов.
6. В первом этапе отклонять асану, уже присутствующую в другом вхождении,
   с `duplicate_catalog_item`. Сравнивать ID и, если UUID есть, UUID без учёта
   регистра. Возможность явно разрешённых повторов можно добавить позже.
7. Создать копию снимка с новым UUID и `parent_uuid` исходного варианта.
   Изменить только `catalog_item` выбранного вхождения. Сохранить его
   `element_id` и позицию, остальные элементы и метаданные — без изменений.
8. Для нового элемента установить `start_mirror = end_mirror = bilateral`,
   как при текущей генерации. Настройки прежней асаны не переносятся вслепую.
9. Атомарно добавить новый снимок и сменить активный UUID. Вернуть
   `ToolMessage` с новым снимком и описанием замены. UI читает результат из
   состояния после применения `Command`; публикация типизированного
   `sequence_committed` остаётся частью расширенного stream-контракта.

Количество и порядок других элементов не меняются. Операция не запускает
генератор для всей секвенции. Невалидные аргументы и ошибки не оставляют
частичных изменений. Проверка исходного UUID и последовательное выполнение
защищают от применения к другому варианту.

## 7. Выбор кандидата и неоднозначности

«Третья»/«последняя» разрешается по актуальному порядку в `element_id`.
Имя исходной асаны разрешается только при единственном совпадении; при
нескольких вхождениях агент спрашивает позицию. «Она» разрешается по истории
только при однозначной ссылке. Если секвенции нет — сначала запросить генерацию.

При запросе конкретной асаны агент ищет её английское имя или известный UUID.
Поиск по имени — частичный: несколько результатов не позволяют молча взять
первый. Если невозможно однозначно определить запрошенную асану, ассистент
показывает варианты и спрашивает выбор.

При запросе категории, например «другая асана стоя», выбор кандидата делегирован
агенту: он учитывает реальные tags, исходные ограничения, соседние элементы,
старт/финиш и отсутствие повторов. Отсутствие пригодного совпадения приводит
к объяснению/уточнению, без ослабления фильтров молча.

Первый этап использует модель для выбора кандидата и детерминированный editor
для применения. `TypeSafeService.choose_next_catalog_item` остаётся частью
генерации: его контракт выбора следующей асаны по префиксу не подходит для
замены в середине готового списка. Отдельная оценка переходов через TypeSafe
может быть добавлена позже. Editor проверяет структуру и источники данных;
теги сами по себе не гарантируют соблюдение всех предпочтений генератора.

## 8. UI и Save

Чат принимает генерацию, поиск, вопросы и редактирование; placeholder отражает
эти действия. Для поиска отображаются реальные названия/изображения и текст
ассистента, без controls сохранения секвенции. Результат замены показывает
новый вариант и короткое сообщение о старом и новом элементе.
Карточка результата замены хранит UUID вариантов всей family в порядке создания,
выбирает новый вариант и позволяет вернуться к исходному через Previous/Next.

Предварительные элементы генерации не доступны для Save или редактирования.
До commit выбранным остаётся предыдущий полный вариант. Во время операции
отправка новых команд и смена варианта блокируются; повторный rerun не запускает
ту же операцию повторно. `request_id` связывает результат с исходной командой.
UI хранит ID и статус уже отправленной команды; обычный rerun только восстанавливает
отображение. Явный повтор после ошибки получает новый `request_id`.

Проекция в существующий импортный формат:

| Поле импорта | Источник |
| --- | --- |
| `info.uuid` | UUID конкретного варианта |
| `info.name`, `info.description`, `info.language` | Метаданные полного снимка |
| `info.elements_count` | Длина `elements` |
| `thumbnails[].uuid` | **Catalog item UUID**, а не локальный `element_id` |
| `thumbnails[].order` | Позиция элемента |
| `start_mirror`, `end_mirror` | Значения выбранного снимка |
| `image_url`, `alt` | Проекция для отображения |

Новый UUID при изменении обязателен: import API с прежним UUID возвращает ранее
сохранённую секвенцию без перезаписи. Повторный Save одного неизменного варианта
сохраняет UUID; новый вариант получает новый UUID даже если его родитель ещё
не сохраняли. См. [правила импорта](../../import_generated.md#правила-конвертации).
Browser handoff и авторизация через страницу Asana Catalog сохраняются.

Save передаёт вариант, выбранный в соответствующей карточке. Снимок с отсутствующим
catalog UUID не отправляется: UI сообщает, что такой элемент нельзя импортировать.
Ограничение импорта `1..75` элементов проверяется перед Save, без скрытого
усечения. Это не вводит новый предел на count существующей генерации.

Для старого формата session messages с одними миниатюрами сохраняется отображение.
При выборе для редактирования можно восстановить полные items точным поиском
каждого catalog UUID с tags. Предлагаемое поведение: выполнить такое восстановление
один раз при активации; если у элемента нет UUID или ответ неоднозначен, оставить
карточку доступной для просмотра и предложить новую генерацию. Не угадывать IDs
или tags по `alt`.

## 9. Другие операции: последующий этап

Добавление, удаление, перемещение и самостоятельное изменение зеркальности
**не входят в первый этап**. Агент объясняет, что они пока недоступны, не
подменяет их генерацией или заменой и не сообщает об их выполнении.
Установка mirror flags по bilateral нового catalog item при замене не является
самостоятельной операцией изменения зеркальности.

Общий механизм версий и адресации допускает следующие tools как последующее
расширение. Точный состав операций и их контракты можно изменить на ревью:

| Операция | Аргументы сверх исходного UUID | Правила |
| --- | --- | --- |
| `insert_sequence_element` | Проверенный catalog item ID, позиция `1..N+1` | Новое вхождение; count +1, пересчёт order |
| `remove_sequence_element` | `element_id` | Удалить одно вхождение; count −1, пересчёт order; не оставлять пустую секвенцию |
| `move_sequence_element` | `element_id`, новая позиция `1..N` | Сохранить вхождения и count, изменить порядок |
| `set_sequence_element_mirroring` | `element_id`, два boolean | Менять только flags; допустимость относительно bilateral нужно определить отдельно |

Все изменения создают новый снимок/UUID, сохраняют родителя и публикуют тот же
`sequence_committed`. Возврат к предыдущему варианту обеспечивается выбором в UI.
Пакетные операции, явное разрешение повторов и перезапись секвенции на сервере
потребуют отдельных контрактов.

## 10. Критерии приёмки

Проверить с fake model/services и Streamlit AppTest:

- После генерации в состоянии сохранены полные items, порядок и исходный запрос.
- Следующий вызов модели видит актуальный снимок, включая IDs и tags.
- Диалог и секвенция сохраняются между reruns; две сессии не обмениваются ими.
- Вопрос о третьем элементе не вызывает генерацию; поиск альтернатив не меняет снимок.
- Замена третьего элемента меняет ровно его catalog item и mirror flags,
  сохраняет count, порядок и остальные вхождения.
- В одном запросе создаётся не более одного изменения: попытка заменить второе
  вхождение с актуальным UUID отклоняется; следующий запрос допускает новую замену.
- Для нескольких запрошенных замен агент уточняет один элемент. Tools добавления,
  удаления, перемещения и изменения зеркальности не зарегистрированы;
  эти операции описаны как последующее расширение с уточнением на ревью.
- Новая версия имеет новый UUID, ссылку на родителя и становится активной;
  исходная версия остаётся доступной.
- Previous/Next/Use this sequence меняют контекст без вызова модели/генератора.
  Отрисовка более поздней карточки не отменяет явный выбор.
- Regenerate старой карточки использует её исходный запрос и выбранную family.
- Неоднозначное имя или местоимение приводит к уточнению, а не изменению.
- Неизвестный candidate ID, устаревший UUID, недоступное вхождение и непригодный
  item оставляют состояние секвенций неизменным.
- Повтор существующей асаны отклоняется; замена на себя возвращает `no_change`.
- Ошибка после нескольких streamed элементов не сохраняет частичную секвенцию.
- Успешный commit не теряется при ошибке последующего текстового ответа или rerun.
- В Save используется catalog UUID, правильный порядок и UUID выбранного варианта;
  повторный Save сохраняет UUID, Save после замены использует новый.
- Legacy thumbnails не превращаются в выдуманный полный catalog-контекст.
