# 006 — Критерии приёмки обмена элементов

Контракт: [README](README.md). Автоматические тесты выполняются на полных
снимках секвенций и тестовых catalog items, без платных модельных вызовов
и внешнего API каталога. Понимание естественных запросов проверяется отдельным
opt-in прогоном живой LLM; обычный unittest его не запускает.

## Сервис и модель варианта

1. **Обмен несоседних элементов.** Для `[A, B, C, D, E]` обмен третьего и пятого
   даёт `[A, B, E, D, C]`. B и D не сдвигаются, `order` равен `1..5`.
2. **Границы.** Проверить соседние элементы, первую и последнюю позиции,
   секвенцию из двух элементов и обратный порядок аргументов. Перестановка
   одной и той же пары даёт одинаковый порядок независимо от аргументов.
3. **Идентичность вхождения.** Каждый перемещённый элемент сохраняет свой
   `element_id`, полный `catalog_item` и оба mirror flags. Проверить разные
   flags, включая `start_mirror != end_mirror` и значения, не совпадающие
   с `bilateral`. Flags перемещаются вместе с вхождением и не пересчитываются.
4. **История.** Новый вариант имеет другой UUID, прежнюю family,
   `parent_uuid` исходного варианта и `operation=swap`. Сохраняются count,
   `generation_request`, name, description и language;
   `operation_request` равен текущему запросу. Исходный снимок не меняется,
   в том числе при последующем изменении возвращённого объекта.
5. **Повтор catalog item.** Два разных `element_id` с одинаковыми catalog
   ID/UUID обмениваются без `duplicate_catalog_item`, сохраняют свои flags
   и создают новый вариант.
6. **Одинаковые UUID вхождения.** Для двух одинаковых существующих IDs сервис
   возвращает `None`, tool — `no_change` с исходным UUID. Проверить также
   секвенцию из одного элемента. Новый вариант и commit отсутствуют.
7. **Неизвестное вхождение.** Неизвестный первый либо второй ID возвращает
   `sequence_element_not_found`. Два одинаковых неизвестных IDs тоже дают
   ошибку, а не `no_change`. Исходный снимок не меняется.
8. **Совместимость.** Снимок `operation=swap` сериализуется и восстанавливается
   с правильными порядком и IDs; старые варианты `generate`, `regenerate`
   и `replace` продолжают читаться.

## Tool, состояние и агент

9. **Реальный цикл tools.** Scripted model вызывает зарегистрированный
   `swap_sequence_elements` для выбранной секвенции. Возвращённый `Command`
   добавляет ровно один снимок, делает его активным и устанавливает общий
   флаг commit. Следующий model call видит новый порядок. `ToolMessage`
   содержит полный снимок и две записи `swap` с правильными old/new positions.
10. **Защита источника.** Отсутствие активного полного снимка даёт
    `sequence_not_found`, UUID другого варианта — `stale_sequence`,
    в том числе для сохранённого варианта той же family. Ни ошибка,
    ни невалидный формат UUID не меняют снимки и активный выбор.
11. **Выбор старого варианта.** После генерации другой family выбрать старый
    вариант и обменять его элементы. Parent и family относятся к выбранному
    источнику, более новый вариант другой family остаётся неизменным.
12. **Общий лимит.** После успешного обмена второй обмен, замена и генерация
    в том же запросе отклоняются. Проверить также обмен после замены или
    генерации, `generation_started=true` и актуальный UUID результата.
    Код — `operation_already_started`. Следующий запрос допускает новый обмен.
13. **Повтор после ошибки.** Ошибка либо `no_change` не устанавливают флаг
    commit; последующий корректный обмен в том же запросе разрешён.
14. **Команды приложения.** При `require_generation=true` обмен возвращает
    `generation_required` и не считается выполненной генерацией.
15. **Зависимости.** При чистом обмене генератор, каталог, tags service
    и TypeSafe не вызываются. Проверить пустой и заполненный
    `latest_catalog_items`: они не влияют на результат и не меняются.
    Обмен первой/второй/последней позы не запускает правила генерации заново.

## Диалог и события

16. **Разрешение пары.** При проверке с моделью команда по двум позициям,
    «первой и последней» и однозначным именам вызывает tool с UUIDs
    актуального снимка. Повтор имени, неоднозначная ссылка или только один
    элемент приводят к уточнению без изменения. Позиция вне `1..N`
    и отсутствие секвенции объясняются без автоматической генерации.
17. **Намерение пользователя.** Вопрос о последствиях обмена получает ответ;
    просьба выполнить обмен, в том числе «Можешь поменять…?», не требует
    повторного подтверждения.
    Для нескольких обменов или обмена и замены ассистент уточняет одну
    операцию. Он не имитирует обмен заменами или Regenerate.
18. **Прогресс.** У нового tool есть этап `updating_sequence` с заголовком
    обмена и корректным summary. При успехе один `sequence_committed`
    появляется после доступности полного снимка в state, с правильными
    request/step/tool IDs. Предварительных `sequence_element` и события
    каталожной галереи нет. Ошибка и `no_change` завершают этап без commit.
19. **Ответ.** Финальный текст на языке пользователя называет обменённые
    позы и позиции по результату tool. Для `no_change` сообщение говорит
    об одном и том же вхождении, без текста о замене кандидата.

## Карточка, история и Save

20. **Отображение и импорт.** У карточки результата выбран новый UUID;
    миниатюры и импортный JSON показывают обменённый порядок, catalog UUIDs
    и исходные flags каждого вхождения. Save передаёт новый `info.uuid`.
    Повторный Save этого варианта сохраняет UUID. Previous/Next позволяют
    вернуться к исходному варианту с прежним порядком.
21. **Rerun и ошибка текста.** Rerun восстанавливает новый вариант и прогресс
    без повторного обмена. Если модель падает после commit, вариант остаётся
    активным и доступным для Save. Ошибка tool и `no_change` не создают
    новой карточки секвенции.
22. **Regenerate.** Regenerate результата обмена использует исходный
    `generation_request` и создаёт обычный вариант `regenerate`;
    обмен автоматически не повторяется.
23. **Регрессии.** Генерация, замена, поиск/показ каталога, переключение
    вариантов, прогресс и Save проходят существующие проверки.

## Проверка реализации

Автоматические проверки сервиса и tool разместить в
`tests/test_sequence_swap.py`; для интеграции переиспользовать существующие
scripted model и проверки вариантов, событий и UI/Save. Проверку понимания
естественных запросов из пунктов 16–17 выполнить отдельно: scripted model
проверяет применение tool calls, но не доказывает выбор инструмента LLM.

После реализации запустить существующий комплект:

```bash
uv run python -m unittest discover -s tests -v
```

В браузере проверить команду обмена, результат и Previous/Next на секвенции
с зеркальными элементами. Фактические результаты записать в README фичи.

Для диалога использовать
[sequence_swap_dialogue.py](../../../tests/fixtures/sequence_swap_dialogue.py):

```bash
uv run --env-file .env python tests/fixtures/sequence_swap_dialogue.py \
  --output /tmp/swap-dialogue.json
```

Он проверяет tool calls и состояние на 16 формулировках; финальные ответы
нужно отдельно просмотреть на язык, смысл уточнения и правильные позиции.
Для браузера использовать
[sequence_swap_browser.py](../../../tests/fixtures/sequence_swap_browser.py):

```bash
uv run streamlit run tests/fixtures/sequence_swap_browser.py --server.port 8516
```

Ввести `Generate a yoga sequence with 5 poses.`, затем
`Поменяй третью и пятую местами`. Проверить порядок, зеркальную Tree pose,
Previous/Next, Rerun через меню и два нажатия Save. Локальный приёмник на 8517
записывает переданные JSON в `/tmp/006-swap-browser`; они должны совпасть
между собой и со snapshot обмена в `state.json`. Внешний каталог не изменяется.
Фактический прогон и артефакты описаны в [результатах реализации](README.md#7-результаты-реализации-и-проверок).
