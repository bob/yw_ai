# 011 — Prompt и tools GPT по действию

Статус: **отменена 14 октября 2026 года; реализация откачена**.

Фича отменена по решению пользователя: профили и маршрутизация по
грамматике не применяются. Выбор инструментов снова полностью передан
модели. Текст ниже сохранён как отменённая спецификация; номер 011
остаётся закреплённым за ней.

Источник задачи — пункт 6 [анализа расхода токенов](../../token-usage-and-optimization.md).
Фича использует [компактные результаты 009](../009-compact-gpt-tool-results/README.md).
Проверки: [acceptance.md](acceptance.md).

## 1. Проблема и результат

Каждый запрос получает около 1985 токенов общего prompt и около 1719 токенов
JSON-описаний семи tools. Запрос добавления несёт подробные правила генерации,
каталога, replacement и swap. После простой успешной операции GPT вызывается
ещё раз для подтверждения результата, уже известного Python.

Ввести стабильные профили контекста: короткое общее ядро, инструкции
конкретного действия и доступные для него tools. В поддерживаемом простом
сценарии результат tool завершает запрос без второго GPT call и без отдельного
текстового подтверждения. Пользователь получает секвенцию или галерею, а не
вступление или дублирующий комментарий над результатом.
Открытые вопросы и сложные запросы продолжают использовать обычный agent loop.

Jev, candidate batches, алгоритм подбора и контекст TypeSafe сохраняются.
Кнопка Generate по-прежнему проходит GPT; её прямой запуск без GPT — пункт 1
исходного анализа и в эту фичу не входит.

## 2. Выбор профиля без дополнительной модели

Профиль выбирается при начале пользовательского запроса и сохраняется
на весь его agent loop. Маршрутизация не вызывает GPT или Jev.

- Обязательные Generate/Regenerate известны из runtime: профиль `generation`.
- Для чата узкий профиль допускается только при однозначном распознавании
  целой простой команды из документированной русской/английской грамматики.
- Сочетание нескольких действий, отдельный вопрос, просьба только объяснить
  последствия, неизвестная формулировка или нераспознанный остаток текста
  выбирают `general`. Одного ключевого слова «добавь» недостаточно.
- При уточнении следующий user request маршрутизируется заново; сложная
  ссылка по прошлому диалогу допускает `general`.

Начальная грамматика должна покрыть «Добавь 3 асаны», «Добавь одну асану в
конец», «Добавь две перед третьей», «Поменяй местами третью и пятую»,
`Add 3 poses`, `Swap the third and fifth poses` и точные команды browsing
или replacement с явно указанными позами. Существующий смысл user request
передаётся tool полностью. Неизвестные дополнительные пожелания сохраняются
через `general`, а не отбрасываются ради узкого профиля.

Распознавание профиля определяет доступные действия; позиции, count,
UUIDs и неоднозначность по-прежнему проверяются моделью и tools.

## 3. Профили и доступные tools

| Профиль | Tools | Инструкции действия |
| --- | --- | --- |
| `generation` | generate, search, tag names | Count/duration, cap 45, явная первая поза, обязательная генерация |
| `addition` | add | Count новых элементов, default 1/end, occurrence anchor, cap по свободному месту |
| `replacement` | search, tag names, replace | Реальный кандидат, позиционные ограничения, неоднозначность |
| `swap` | swap | Два существующих occurrences, позиции/имена, отсутствие подбора |
| `catalog` | search, tag names, show | Проверенные кандидаты и одна явная галерея |
| `general` | Все семь | Полный набор поддерживаемых действий в сокращённой форме |

Имена в таблице соответствуют существующим `ASSISTANT_TOOLS`. В каждом профиле
порядок tools фиксирован и является подпоследовательностью общего registry.
Agent registry остаётся полным, фильтруется набор schemas конкретного request.
Возвращённый моделью tool вне профиля не выполняется и даёт существующий
тип ошибки, без автоматического расширения списка в середине запроса.

Добавление использует внутренний каталог генератора и не требует публичных
search/tag tools. Запрос «найди кандидатов, пока не меняй» не попадает в
`addition` или `replacement`.

## 4. Общее ядро и сохранение поведения

Ядро кратко задаёт: реальные данные и UUIDs; authoritative текущий snapshot;
английский каталог и ответ на языке пользователя; один tool за раз; максимум
одна успешная sequence operation; отсутствие операций удаления/произвольного
перемещения/независимого mirroring; уточнение неоднозначности; отсутствие
выдуманных изменений и poses.

Детали действий добавляются только к нужному профилю. Повторяющиеся объяснения
алгоритма, выполненного Python, сокращаются, но инструкции для правильных
аргументов и объяснения результатов остаются. Проверки в tools выполняются
независимо от prompt: cap, stale UUID, допустимые occurrences, mirror flags,
атомарность, generation-required и общий operation limit.

Целевые локальные бюджеты статического prompt плюс tools, без истории/snapshot:

| Профиль | Верхняя цель, токены |
| --- | ---: |
| `addition`, `swap` | 1400 |
| `generation`, `replacement`, `catalog` | 2000 |
| `general` | 3000 |

Числа считаются тем же `o200k_base` и сериализацией schemas, что baseline 3704
из анализа; служат воспроизводимой локальной метрикой, а не обещанием exact
API usage. Бюджет нельзя выполнять удалением обязательного поведения.

## 5. Результат tool без дублирующего текста

Для узкого профиля с одним запросом действия и без отдельного открытого
вопроса после подтверждённого успеха завершить запрос локально, без второго
GPT call. Generate/Regenerate, add, replacement и swap показывают полученную
секвенцию; catalog — галерею после успешного show commit/display. Обычный
успех не требует отдельного `AIMessage` или публичного
`AssistantMessageEvent(purpose=final)`: тексты «Готово», «Сгенерирована
последовательность из 9 асан» и аналогичные подтверждения не добавляются.

Не публиковать сопровождающий текст модели из сообщений с tool calls
(`purpose=intermediate`), например «Сейчас подберу асаны». Это правило действует
и для `general`. Структурированный progress инструмента остаётся. Полные
сообщения модели и результаты tools сохраняются в canonical `messages`
для корректного agent loop; отсутствие публичного комментария не меняет
протокол вызова tools.

Текст нужен, когда он сообщает то, чего недостаточно увидеть в результате:
уточнение, ошибку, причину `no_change`, существенное ограничение запроса или
ответ на отдельный вопрос. Для простых ru/en команд такие пояснения можно
сформировать локально из структурированных фактов результата 009:

- Generate/Regenerate: при фактическом ограничении запроса пояснить лимит 45.
  Число элементов брать из результата, не из оценки duration. Флаг фактического
  ограничения, если нужен, хранить отдельно от model payload; duration и
  bilateral уже обрабатываются генератором.
- Add: только при `limit_applied` сообщить запрошенное и фактическое количество
  (`added_count`) и cap 45, а не добавлять подтверждение обычного успеха.
- Известный `no_change`: объяснить, что лимит достигнут, выбранная поза уже
  стоит на месте или указан один occurrence дважды, без claim успеха.

Локальный путь включается только при заранее известном языке ru/en и условиях,
для которых хватает структурированных фактов. Сложный смешанный запрос,
другой язык, недостаточные факты или необходимость объяснения получают
обычное завершение через GPT. `general` не завершать локально автоматически;
итоговый текст должен отвечать на вопрос или объяснять результат, а не
дублировать успешную карточку стандартным подтверждением. Ошибки в
аргументах/поиске и неоднозначность остаются в model loop, чтобы сохранить
возможность уточнить или исправить вызов.

Не выполнять tool повторно ради подготовки текста. Локальное завершение
происходит после доступности commit в state; запрос и результат сохраняются
в execution history и воспроизводятся без обязательного итогового текста.
Если нужно локальное пояснение, сохранить его в `messages` и опубликовать
обычный `AssistantMessageEvent(purpose=final)` ровно один раз после commit.
При ошибке подготовки пояснения уже сохранённый вариант остаётся доступен
UI/Save, как сейчас.

## 6. Эффект и интеграция

Для простой команды Generate 9 и простого добавления 3 после неё целевой
обычный путь — по одному GPT call на действие вместо двух, без новых routing
calls; Jev по-прежнему делает обычно 8 + 3 вызова. Для replacement с поиском
и catalog цепочки вызовов остаются, но последний GPT call для простого
подтверждения пропускается. Calls суммаризации 010 учитываются отдельно.

В model middleware использовать устойчивый профиль и request override;
не создавать независимого агента/нового thread для каждого действия.
Progress должен корректно завершать запрос и без финального текста; локальные
существенные пояснения проходят обычный публичный event. Нельзя показывать
фиктивный GPT thinking с заявлением вызова API или пустой этап подготовки
ответа, когда пользователю достаточно результата tool.

Проверки и итоговые измерения должны различать уменьшение контекста и
уменьшение числа GPT calls. Простой и general пути сравниваются отдельно.
