# Расход токенов при Generate и добавлении элементов

Дата анализа: 13 октября 2026 года.

Расход идёт в двух независимых местах: GPT управляет действиями, а TypeSafe/Jev выбирает позы. Текущая `.env` и общий default используют `openai:gpt-6-luna` с `reasoning_effort="none"`. Численные примеры ниже относятся к прежним замерам; они не являются измерениями Luna. См. [миграцию 014](specs/014-gpt-6-luna/README.md).

Это разбор по текущему коду и локальный подсчёт постоянного контекста, а не измерение оплаченного запроса. Платные вызовы для проверки не запускались. Внешние переменные окружения могут переопределять настройки `.env`.

## При клике Generate

Кнопка формирует готовый запрос вида `Generate a yoga sequence with 9 poses.` и отправляет его основному агенту. См. [обработчик кнопки](../src/langchain_app/assistant.py).

| Этап | Где тратятся токены |
| --- | --- |
| 1. GPT выбирает `generate_sequence` | **Вход:** системный prompt, описания всех семи tools, история, текущая выбранная последовательность. **Выход:** аргументы вызова tool и возможный промежуточный текст. |
| 2. Загружается каталог | Обычный HTTP-запрос. Сам по себе токены моделей не расходует. |
| 3. Выбирается первая поза | Случайный выбор в Python либо указанный ID. Вызова Jev нет. |
| 4. Выбираются остальные позы | Обычно **один вызов Jev на каждую позу**. Каждый получает запрос, правила, все уже выбранные позы и кандидатов с названиями и тегами. |
| 5. GPT формирует итоговый ответ | Повторно получает системный prompt, tools и историю. Новая последовательность передаётся **дважды**: в результате tool и в текущем snapshot. Затем GPT пишет ответ пользователю. |

Для **9 элементов обычно получается 2 вызова GPT + 8 вызовов Jev**. Если кандидат единственный, Python выбирает его без Jev.

Связанные участки кода:

- [Запуск и сохранение состояния агента](../src/langchain_app/services/assistant_agent.py): `AssistantAgent._get_agent()` и `stream_response_events()`.
- [Цикл генерации](../src/langchain_app/services/sequence_generator.py): `SequenceGenerator.generate()`.
- [Выбор Jev](../src/langchain_app/services/type_safe.py): `choose_next_catalog_item()` и `_choose_catalog_item()`.

## При последующем запросе «Добавь 3 элемента»

| Этап | Где тратятся токены |
| --- | --- |
| 1. GPT определяет добавление | Получает всю историю, текущий snapshot, prompt и семь tools. Возвращает `add_sequence_elements` с количеством и местом вставки. |
| 2. Загружается каталог | HTTP-запрос без расхода токенов моделей. |
| 3. Выбираются три новые позы | Обычно **3 вызова Jev**. Каждый получает исходный запрос генерации, новый запрос, правила, **всю исходную последовательность**, ранее выбранные добавления и кандидатов. |
| 4. GPT сообщает результат | Получает старый результат генерации из истории, полный результат добавления и новый snapshot. Пишет итоговый текст. |

Исходные позы повторно не подбираются, но их данные повторно отправляются моделям.

Связанные участки кода:

- [Tool добавления](../src/langchain_app/tools/sequence.py): `add_sequence_elements()`.
- [Подбор новых элементов](../src/langchain_app/services/sequence_generator.py): `SequenceGenerator.add_elements()`.
- [Контекст Jev при добавлении](../src/langchain_app/services/type_safe.py): `choose_addition_catalog_item()`.

Итого для сценария **Generate 9 → добавить 3**: обычно **4 вызова GPT + 11 вызовов Jev**, без дополнительных поисков и повторных попыток.

Это обычный успешный путь. Уточняющие вопросы, дополнительные tools, ошибки или повторные попытки меняют число вызовов. Единственный кандидат позволяет пропустить вызов Jev; отсутствие места в пределах лимита 45 элементов останавливает подбор добавлений.

## Что особенно увеличивает расход

### Постоянный контекст GPT

Локальный подсчёт токенизатором `o200k_base` дал:

| Часть контекста | Токены |
| --- | ---: |
| Системный prompt | 1 985 |
| JSON-описания семи tools | 1 719 |
| Суммарно | 3 704 |

Это около **3 700 токенов на каждый вызов**, ещё до истории и последовательности. Два вызова отправляют этот объём дважды.

Это оценка текста, а не точный счёт API: JSON-представление schemas отличается от внутреннего представления tools у провайдера; служебное оформление сообщений и скрытые инструкции провайдера в подсчёт не включены. Числа относятся к версии кода на дату анализа.

### Дублирование последовательностей

Полный snapshot сохраняется в `ToolMessage`, а middleware снова добавляет текущую последовательность перед каждым вызовом. В tool-результате остаются и `image_url`, хотя из текущего snapshot они исключены.

После генерации первый запрос добавления получает старую последовательность и в истории, и как текущий snapshot. После добавления итоговый вызов GPT получает старый результат генерации, полный новый результат добавления и новый snapshot.

См. [результаты sequence tools](../src/langchain_app/tools/sequence.py), [middleware текущего snapshot](../src/langchain_app/services/sequence_context.py) и [проекцию последовательности для модели](../src/langchain_app/schemas/generated_sequence.py).

### Накопление истории

Старые полные результаты остаются в сообщениях. Обрезки или суммаризации сейчас нет. Новые запросы отправляют накопленную историю повторно.

См. [состояние и checkpointer агента](../src/langchain_app/services/assistant_agent.py).

### Повтор контекста Jev

При генерации на `n` поз уже выбранные элементы пересылаются суммарно:

```text
1 + 2 + ... + (n - 1) = n(n - 1)/2
```

Для 9 поз это **36 описаний элементов**, помимо кандидатов.

При добавлении `m` элементов к `n` исходным пересылаются:

```text
n + (n + 1) + ... + (n + m - 1) = n×m + m(m - 1)/2
```

Для 9 + 3 это **30 описаний**. Формулы описывают обычный путь, в котором на каждом шаге вызывается Jev. Это число повторов описаний, а не число токенов: длина названий, тегов и дополнительных полей различается.

См. [построение контекста TypeSafe](../src/langchain_app/services/type_safe.py).

### Большой финальный набор кандидатов

Обычно берётся до 10 кандидатов, но для последнего элемента ограничение не применяется: могут отправиться все finishing-позы либо все доступные позы.

См. `_candidate_batch()` в [генераторе](../src/langchain_app/services/sequence_generator.py).

### Как учитывается результат tool

JSON результата tool создаёт Python. Он расходует **входные токены следующего вызова GPT**, а не выходные токены генерации GPT.

Выход GPT включает аргументы вызова tool, возможный промежуточный текст и финальный ответ пользователю. Jev имеет отдельные входные и выходные токены; его расход нужно учитывать отдельно от OpenAI.

## Где оптимизировать, по приоритету

1. **Убрать GPT из пути кнопки Generate.** Количество и действие уже известны из формы. Можно непосредственно запускать генератор, сохранять результат и показывать шаблонное подтверждение. Для Generate 9 это уберёт **оба вызова GPT**, оставив обычно 8 вызовов Jev. При реализации нужно сохранить текущую обработку progress, commit и ошибок.

2. **Сделать результаты tools короткими.** Полные последовательности уже хранятся в `state.sequences`. В сообщение модели достаточно вернуть статус, UUID, количество и краткое описание изменения. Это уберёт повтор полных snapshots, URL изображений и их дальнейшее накопление в истории. Актуальная последовательность по-прежнему доступна через текущий snapshot.

3. **Сократить контекст Jev.** Сейчас передаются UUID, occurrence ID, mirror-флаги и другие поля, хотя сохранение исходных элементов и исключение повторов выполняет Python. Для выбора можно оставить названия, нужные теги, ближайших соседей и сводку всей последовательности: есть ли twist, тип предыдущей позы, требования к завершению. Здесь нужно проверить качество подбора, включая вставку в середину и переход к фиксированному суффиксу.

4. **Ограничить историю GPT.** Оставлять последние ходы и необходимые предпочтения пользователя. Текущий snapshot уже служит источником актуального состояния. LangChain поддерживает обрезку и суммаризацию истории; суммаризация сама требует дополнительных вызовов модели. См. [документацию LangChain](https://docs.langchain.com/oss/python/langchain/short-term-memory).

5. **Ограничить кандидатов и на финальном шаге.** Формировать небольшой релевантный набор из finishing-поз. Размер списка сейчас может неожиданно увеличивать один запрос Jev.

6. **Сократить prompt и набор tools для конкретного действия.** Запрос добавления не требует всех подробных инструкций про browsing, swap и replacement. Для простого добавления также можно оставить один вызов GPT для разбора запроса, а подтверждение формировать кодом.

7. **Улучшить prompt caching.** Меняющийся snapshot сейчас добавляется в системное сообщение перед историей, что сокращает общий совпадающий префикс между операциями. Стабильные инструкции и tools стоит держать в начале, динамическое состояние — ближе к концу. Кэш уменьшает стоимость совпавших входных токенов; результат нужно проверять по `cached_tokens`. См. [OpenAI Docs](https://developers.openai.com/api/docs/guides/prompt-caching).

## Что само по себе токены не расходует

- Отрисовка карточек и загрузка изображений в интерфейсе.
- Progress-события и их сохранение для повторного отображения.
- Переключение уже сохранённых вариантов последовательности.
- Обычные Streamlit rerun, если не запущен новый запрос к агенту.
- Создание и переиспользование клиентов через `st.cache_resource`.
- Детерминированные проверки, сборка snapshots и сохранение состояния в Python.

`st.cache_resource` переиспользует клиентов, но не кэширует ответы моделей. Обычный HTTP-запрос к каталогу сам по себе не является вызовом GPT или Jev. При этом текстовые URL изображений, попавшие в сообщения модели, занимают входные токены.

Названия progress-этапов не равны количеству вызовов модели. Например, `Preparing response...` публикуется при обработке уже полученного финального ответа и само по себе не запускает ещё один вызов GPT.

См. [progress middleware](../src/langchain_app/services/response_progress_middleware.py) и [зависимости приложения](../src/langchain_app/dependencies.py).

## Как получить точные суммы

Нужно агрегировать по одной операции usage GPT и Jev отдельно. LangSmith включён в `.env`, а установленный TypeSafe-клиент уже передаёт туда usage; в интерфейсе приложения общего счётчика пока нет.

Для каждого пользовательского запроса полезно собирать:

- Число вызовов GPT и Jev.
- Входные и выходные токены каждого вызова.
- Кэшированные входные токены GPT.
- Reasoning-токены GPT, если используемая модель и настройки их включают.
- Итоговую стоимость отдельно для OpenAI и TypeSafe по применимым тарифам.

API TypeSafe возвращает `input_tokens` и `output_tokens`. См. [документацию TypeSafe](https://docs.typesafe.ai/api).

По официальной документации `gpt-5.1` использует `reasoning.effort=none` по умолчанию; приложение явно не задаёт этот параметр. Поэтому наличие reasoning-расхода следует устанавливать по реальному usage, а не предполагать его по названию модели. См. [OpenAI Docs о GPT-5.1](https://developers.openai.com/api/docs/models/gpt-5.1).
